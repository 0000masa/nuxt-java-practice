# オブジェクトとクラス — 3 言語(Java / PHP / TypeScript)での立ち位置の違い

「オブジェクトとクラスって何が違うの? オブジェクトはクラスの一部みたいな扱い? TS はクラスをあまり使わない印象があるけど、それはオブジェクトが扱いやすいから?」という疑問に答える学習メモ。結論を先に言うと:

- **オブジェクトはクラスの「一部」ではない。** クラスが**設計図**、オブジェクトがそこから作られた**実体**。包含関係ではなく「生成元と産物」の関係。
- **Java / PHP は「クラスが先」。** すべてのオブジェクトはクラスから生まれ、**クラス無しにオブジェクトは存在できない**。
- **TypeScript / JavaScript は「オブジェクトが先」。** `{}` が単独で存在でき、`class` は後から足された**糖衣構文**(オブジェクトを量産する道具の一つ)にすぎない。
- **だから TS はクラスが少ない。** ただし理由はそれだけでなく、**Java は関数を単体で置けず必ずクラスに入れないといけない**という逆方向の制約も効いている。

## 1. オブジェクトとクラスの違い — たい焼きの型と、たい焼き

まずここをはっきりさせる。**クラスは「設計図(型)」、オブジェクトは「その設計図から作られた実体」**。

- **クラス** = たい焼きの**焼き型**。形を決めているが、それ自体は食べられない
- **オブジェクト** = その型で焼いた**たい焼き**そのもの。1 個 1 個が別の実体

```java
// Dog というクラス(設計図)は 1 つ
class Dog {
    private String name;
    Dog(String name) { this.name = name; }
}

// そこから作るオブジェクト(実体)は何個でも。それぞれ別の中身を持つ
Dog a = new Dog("ポチ");   // オブジェクト①
Dog b = new Dog("ハチ");   // オブジェクト②(①とは別物)
```

`new` が「型を使ってたい焼きを 1 個焼く」操作にあたり、これを**インスタンス化**と呼ぶ。できたものは**インスタンス**(オブジェクトとほぼ同義。「クラスから作られた」ことを強調した言い方)。

### 「オブジェクトはクラスの一部?」への答え

**いいえ。** クラスの中にオブジェクトが入っているわけではありません。関係は逆で、**クラスという設計図から、オブジェクトが外に生み出される**。

```
クラス Dog(設計図・1 つ)
   │  new
   ├──→ オブジェクト a(name="ポチ")
   └──→ オブジェクト b(name="ハチ")
```

紛らわしくなる理由は、Java/PHP では**「クラスを見ないとオブジェクトの姿が分からない」**から。オブジェクトがどんなプロパティ・メソッドを持つかはクラスに書いてあるので、「オブジェクト = クラスの中身が実体化したもの」に見える。この感覚自体は Java/PHP では正しい。ただし後で見るように、**TS/JS ではその前提が崩れる**(クラスを見なくてもオブジェクトが作れる)。

## 2. Java / PHP — クラスが先。オブジェクトはクラスから生まれる

Java と PHP では、**すべてのオブジェクトがクラスから生まれる**。「クラスに属さない裸のオブジェクト」は作れない。

```java
// Java: データを 3 つ持ち運びたいだけでも、まずクラス(や record)が必要
record UserSummary(Long id, String username, String displayName) {}
UserSummary u = new UserSummary(1L, "taro", "太郎");

// こう書くことはできない(オブジェクトリテラルが存在しない)
// var u = { id: 1, username: "taro" };   // ❌ Java にこの文法は無い
```

実際このプロジェクトの backend も、API のデータの形をすべてクラス(`record`)で定義している。

```java
// backend/.../post/dto/TimelineResponse.java — データを運ぶだけでもクラス(record)
public record TimelineResponse(List<PostResponse> posts, Long nextCursor) {}
```

### Java にはもう一つ強い制約がある — 関数をクラスの外に置けない

ここが「Java がクラスだらけに見える」大きな理由。**Java ではメソッド(関数)を単体で書けず、必ずどこかのクラスの中に置かないといけない。** プログラムの入口である `main` すらクラスの中にある。

```java
// ❌ Java ではこう書けない。関数だけをファイルに置くことは不可
String formatDate(String iso) { ... }

// ✅ 必ずクラスに入れる
class DateUtils {
    static String formatDate(String iso) { ... }
}
```

つまり **Java がクラスを多用するのは「選んでいる」だけでなく「そうせざるを得ない」面もある**。クラスは Java において、設計図であると同時に「コードの置き場所」も兼ねている。

PHP も同じくクラスベースだが、**関数は単体で書ける**(`function foo() {}` をファイルに直接置ける)点で Java より緩い。そしてもう一つ、次章の抜け道を持っている。

## 3. PHP は中間 — クラスベースだが「連想配列」という抜け道がある

PHP のオブジェクトは Java と同様クラスから作るが、**PHP には連想配列という手軽なデータの入れ物がある**。そのため実務では「わざわざクラスを作らず連想配列で済ませる」ことが多い。

```php
// PHP: クラスを作らずデータを持ち運ぶなら、連想配列が定番
$user = ['id' => 1, 'name' => '太郎'];
echo $user['name'];

// stdClass(名前のない汎用クラス)を使う手もある。json_decode の既定の戻り値がこれ
$user = json_decode('{"id":1,"name":"太郎"}');   // stdClass のインスタンスになる
echo $user->name;
```

この連想配列は、**使い勝手が TS のオブジェクトリテラルに近い**。だから PHP は「オブジェクトの仕組みは Java 型(クラス必須)だが、手軽なデータの扱いは TS 型(リテラルで済ます)」という**中間の立ち位置**にいる。

ただし連想配列には弱点がある。**キーの打ち間違いや項目の欠落を型で守れない**(`$user['nmae']` と書いてもエラーにならない)。そのため近年の PHP では、PHPDoc の `array{id: int, name: string}` 記法(PHPStan / Psalm が検査してくれる)や、素直に DTO クラスを作る方向に寄せることが増えている。

## 4. TypeScript / JavaScript — オブジェクトが先。class は後から来た

TS/JS が根本的に違うのはここ。**オブジェクトはクラスと無関係に、単独で存在できる。**

```typescript
// クラスを一切定義せずにオブジェクトが作れる
const user = { id: 1, username: "taro", displayName: "太郎" }

// 関数も単体で置ける(クラスに入れる必要がない)
export function formatDate(iso: string) { return new Date(iso).toLocaleDateString() }
```

そして重要なのが歴史的な順番。**JavaScript にはもともと `class` が無かった。** `class` は 2015 年(ES2015)に後から追加された記法で、しかも**新しい仕組みを足したのではなく、それまで関数とプロトタイプで書いていたものを「クラス風に書けるようにした」**もの。これを**糖衣構文**と言う。

### 糖衣構文(シンタックスシュガー)とは

**糖衣構文**とは、**すでにできることを、より読みやすく書けるようにしただけの記法**のこと。「糖衣」=砂糖のコーティングで、**中身(できること)は変わらず、見た目だけ甘く飲みやすくした**というイメージ。英語の syntactic sugar そのままの訳。

身近な例で言うと、`i = i + 1` を `i++` と書けるのも糖衣構文。`i++` は新機能ではなく、同じ処理の短い書き方にすぎない。

JS の `class` もこれにあたる。`class Dog { ... }` は内部的には、それ以前から使われていた**関数とプロトタイプ**の仕組みの上に、クラスらしい書き方を被せたもの。(厳密には `class` 独自の挙動もいくつかあるが、「まったく新しい土台が入ったわけではない」という理解でよい。)

補足として、JS/TS は**プロトタイプベース**という方式の言語で、Java/PHP の**クラスベース**とは土台が違う。「クラスが中心にある言語」ではなく「オブジェクトが中心にあり、オブジェクトが別のオブジェクトを親として参照する言語」。深掘りは不要だが、**`class` が言語の中心ではなく後付けの便利記法**という点だけ押さえておくと、次章の話が腑に落ちる。

つまり TS/JS における関係はこうなる。

- Java / PHP: **クラス → オブジェクト**(クラスが先、オブジェクトは産物)
- TS / JS: **オブジェクトが中心。class はオブジェクトを量産する道具の一つ**(無くても困らない)

> 細かい注記: JS の `{}` も内部的には `Object` の仲間なので「クラスと完全に無縁」ではない。ここで言いたいのは **自分でクラスを定義する必要がない**、という意味。

## 5. 3 言語の比較表

| | オブジェクトの作り方 | クラス無しでデータを持てるか | 関数をクラスの外に置けるか | 手軽なデータの入れ物 |
|---|---|---|---|---|
| **Java** | `new` のみ | ❌ 不可(必ずクラス/record) | ❌ **不可**(必ずクラス内) | `record` / クラス(DTO) |
| **PHP** | `new` のみ | ✅ 可(連想配列 / `stdClass`) | ✅ 可 | **連想配列** |
| **TypeScript** | `{}` リテラル or `new` | ✅ 可(オブジェクトリテラル) | ✅ 可 | **オブジェクトリテラル** |

Java が一番厳格(すべてクラス)、TS が一番自由(オブジェクトも関数も単体で置ける)、PHP がその中間。

## 6. だから TS ではクラスをあまり使わない — このプロジェクトが実例

「TS はクラスをあまり使わない印象」は**正しい**。このリポジトリの frontend を実際に調べると、**自分で定義したクラスは 1 つもない**。

- `frontend/app/` 内の `class` 定義 … **0 件**
- `new` が登場するのは `new IntersectionObserver(...)`(`app/pages/index.vue`)と `new Date(...)`(`app/utils/formatDate.ts`)の 2 か所だけ。どちらも**ブラウザ / JS 標準の組み込みクラス**で、自分で作ったものではない
- ロジックの置き場は `app/composables/`(関数)と `app/utils/`(関数)

たとえば API 通信をまとめている composable は、**クラスではなく「関数がオブジェクトを返す」形**になっている。

```typescript
// frontend/app/composables/usePosts.ts
export function usePosts() {
  const fetchTimeline = (params) => $fetch<Timeline>('/api/posts', { params })
  const fetchPost = (id) => $fetch<Post>(`/api/posts/${id}`)
  // ...
  return { fetchTimeline, fetchPost, createPost, deletePost }   // オブジェクトリテラルで返す
}
```

**同じ役割を backend の Java では `PostService` というクラスが担っている。** 「API とやり取りする処理をまとめる」という目的は同じで、道具が関数とクラスに分かれている。

### TS でクラスが少ない理由(5 つ)

1. **オブジェクトと関数で足りる。** 上の `usePosts()` のように、関数の中に変数を閉じ込めてオブジェクトで返せば、クラスの「状態＋メソッド」と同じことができる(クロージャという仕組み)。
2. **フレームワークが関数前提の設計。** Nuxt / Vue の Composition API(や React の hooks)は関数を組み合わせる思想で作られている。クラスで書く方が逆に不自然。
3. **API から来るデータが素の JSON オブジェクト。** サーバから届くのは `{ id: 1, body: "..." }` という素のオブジェクト。TS は構造的型付けなので **interface を貼るだけでそのまま型安全に扱える**。クラスに詰め替える必然性が薄い(Java は逆に、JSON を受け取るのに `record`/クラスが必要)。
4. **モジュールが「置き場所」の役割を果たす。** Java ではクラスがコードの置き場も兼ねるが、TS ではファイル(モジュール)から関数を直接 `export` できる。**クラスを容れ物として使う必要がない。**
5. **多態のためにクラス階層が要らない。** 構造的型付けなので、共通の形を満たすオブジェクトを同じように扱える。継承ツリーを組む動機が弱い(→ [interface-vs-type.md](./typescript/syntax/interface-vs-type.md))。

そして冒頭で触れたとおり、**逆方向の要因**も見落とせない。Java がクラスだらけなのは「クラスが優れているから選んだ」というより、**関数を単体で置けないので他に選択肢がない**という制約も大きい。「TS がクラスを避けている」と「Java がクラスを強制している」の両方が効いて、見た目の差が生まれている。

## 7. それでも TS でクラスを使う場面

「クラスは不要」と覚えてしまうと行き過ぎ。TS でもクラスが適した場面はある。

**(a) 独自のエラー型を作るとき** — 最頻出のケース。

```typescript
class ApiError extends Error {
  constructor(public status: number, message: string) {
    super(message)     // 親 Error のコンストラクタを呼ぶ(super は Java と同じ考え方)
  }
}

try {
  // ...
} catch (e) {
  if (e instanceof ApiError) {   // ← クラスなので instanceof で判定できる
    console.log(e.status)
  }
}
```

**(b) 実行時に型を判定したいとき** — interface は実行時に消えるので `instanceof` が使えない。**実行時に残る必要があるならクラス**を使う(→ [interface-vs-type.md の 6 章](./typescript/syntax/interface-vs-type.md))。

**(c) 状態と振る舞いを持つ実体をたくさん作るとき** — ゲームのキャラクター、エディタのドキュメントなど、「同じ種類のものを何個も作り、それぞれが状態を持って動く」場合はクラスが素直。

**(d) ライブラリがクラス前提のとき** — NestJS(バックエンド)、TypeORM(ORM)、Angular などはデコレータ付きのクラスを前提に設計されている。その世界では素直にクラスを使う。

まとめると、**「データを運ぶだけ」ならオブジェクト＋interface、「実行時に区別したい・状態と振る舞いを持つ実体」ならクラス**、が TS での使い分けの目安。

## つまずきポイント

- **「オブジェクトはクラスの一部」ではない。** クラスは設計図、オブジェクトはそこから生まれた実体。包含ではなく生成の関係。
- **インスタンスとオブジェクトはほぼ同義。** 「インスタンス」は「クラスから作られた」ことを強調した言い方。
- **Java で「関数だけ書きたい」はできない。** `static` メソッドとしてクラスに置くのが定石(`DateUtils.formatDate(...)` のような形)。
- **TS の `class` は「飾り」ではない。** 糖衣構文とはいえ実行時に本物として残る。interface(消える)とは別物なので、`instanceof` したいならクラス。
- **PHP の連想配列は型で守られない。** `$user['nmae']` の打ち間違いに気づけない。規模が大きくなるなら PHPDoc の array shape か DTO クラスへ。
- **TS でクラスを使うのは「悪」ではない。** 独自 Error やライブラリ都合では素直に使う。少ないのは「必要な場面が少ない」だけ。

## 用語集

- **クラス** — オブジェクトの設計図(型)。どんなプロパティ・メソッドを持つかを定める。それ自体は実体ではない。
- **オブジェクト** — 実際にメモリ上にできた実体。プロパティに具体的な値を持つ。
- **インスタンス** — クラスから作られたオブジェクト。オブジェクトとほぼ同義で、出自を強調する言い方。
- **インスタンス化** — クラスからオブジェクトを作ること。Java/PHP/TS いずれも `new` で行う。
- **オブジェクトリテラル** — `{ id: 1, name: "a" }` のように、クラスを定義せずその場で書けるオブジェクト。TS/JS にはあり、Java/PHP には無い。
- **糖衣構文(シンタックスシュガー)** — すでにできることを読みやすく書けるようにしただけの記法。中身は変わらない。`i++` や JS の `class` がこれ。
- **クラスベース** — クラスを中心に据えた方式。Java / PHP がこれ。オブジェクトは必ずクラスから作る。
- **プロトタイプベース** — オブジェクトを中心に据え、オブジェクトが別のオブジェクトを親として参照する方式。JS/TS がこれ。
- **連想配列(PHP)** — `['id' => 1]` のようなキー付きの配列。PHP で手軽にデータを持ち運ぶ定番の入れ物。
- **stdClass(PHP)** — 名前のない汎用クラス。`json_decode` の既定の戻り値がこれ。
- **クロージャ** — 関数が、自分の外側の変数を覚えたまま持ち歩く仕組み。TS でクラスの代わりに「状態＋振る舞い」を作れる理由。
- **DTO** — データを運ぶためだけの入れ物(Data Transfer Object)。TS では interface、Java では `record` で表す。
