# VPC の入口と出口 — 外からの通信はどこで止まるのか

「IGW へのルートがないサブネットには外から届かない」とよく言われる。
では、どこで、なぜ止まるのか。UDP ならどうか。RDS や Redis のセキュリティグループを全開放したらどうなるか。
これらを、このリポジトリの `cloudformation/app.yml` の VPC 構成に沿って整理する。

関連 → [ElastiCache](../redis/elasticache.md) / [フェーズ13 設計書](../../superpowers/specs/2026-08-19-phase13-cloudformation-design.md)

## まず結論(4 行)

- 外から届くかどうかは、まず**パブリック IP があるか**で決まる。プライベート IP は、インターネットから宛先として指定できない
- サブネットのルートテーブルが決めるのは、そのサブネットから**出ていく**通信の経路。IGW が入口でルートテーブルを見てパケットを捨てることはない
- パブリック IP があるのに IGW へのルートがないと、**行きは届くが帰りの経路がない**。TCP は成立しないが、UDP の片道のパケットは届く
- 入口の防御は**セキュリティグループと NACL の役割**。ルートテーブルはアクセス制御の仕組みではない

## 1. IGW がしていること

IGW(Internet Gateway)の仕事は次の 2 つ。

| 向き | IGW がすること |
| --- | --- |
| 外 → VPC | 宛先のパブリック IP を、対応するプライベート IP(`10.0.x.x`)に変換して VPC に入れる |
| VPC → 外 | 送信元のプライベート IP を、対応するパブリック IP に戻して送り出す |

この変換は 1 対 1 の NAT で、「パブリック IP(または EIP)が付いた ENI」にだけ働く。
パブリック IP を持たないリソースには変換先の対応表がないので、外からその宛先に届く経路は存在しない。

VPC に入ったパケットは、宛先が VPC 内のアドレスなので、VPC のルーティング(`local` ルート)で宛先の ENI に届けられる。
**このとき、宛先サブネットのルートテーブルに `0.0.0.0/0 -> igw` があるかどうかは関係しない。**

入ってくる通信の経路を変えたいときは、IGW 自体にルートテーブルを関連付ける機能がある(Ingress Routing / エッジアソシエーション)。
たとえば検査用のアプライアンスを経由させる、といった使い方をする。
これは明示的に設定する機能で、デフォルトの動作ではない。

## 2. IGW へのルートがないサブネットに ALB を置いたら

インターネット向け ALB(ALB ノードはパブリック IP を持つ)を、`0.0.0.0/0 -> igw` を持たないサブネットに置いた場合を考える。

### 行き: 届く

1. クライアントから、ALB のパブリック IP 宛てのパケットが IGW に届く
2. IGW が宛先を ALB ノードのプライベート IP に変換する
3. `local` ルートで ALB ノードの ENI に届く(セキュリティグループが許可していれば)

### 帰り: 経路がない

ALB はクライアントのパブリック IP(例: `203.0.113.5`)へ応答を返そうとする。
宛先は VPC の外なので、**ALB がいるサブネットのルートテーブル**で経路が決まる。

| ルートテーブルの状態 | 結果 |
| --- | --- |
| `0.0.0.0/0` のルートがない | 送り先が見つからず、パケットが破棄される |
| `0.0.0.0/0 -> NAT` | NAT を通るので、送信元 IP が NAT の EIP に変わる。クライアントは「自分が送った相手とは別の IP から返事が来た」と判断して破棄する |
| `0.0.0.0/0 -> igw` | IGW が送信元を ALB のパブリック IP に戻して返す。通信が成立する |

### TCP ではハンドシェイクが完了しない

HTTP/HTTPS で使う TCP は、3 ウェイハンドシェイクが終わらないと通信を始められない。

1. **クライアント → ALB:** `SYN`。**届く**
2. **ALB → クライアント:** `SYN-ACK`。**帰りの経路がないので届かない**
3. **クライアント → ALB:** `ACK`。手順 2 が届かないので送られない

クライアントから見ると、`SYN` を送っても応答がないまま接続タイムアウトになる。
行きのパケットは届いているのに、クライアント側からは「リクエストすら送れていない」ように見える。

したがって、ALB をインターネットに公開するときは、ALB のサブネットに `0.0.0.0/0 -> igw` を持つルートテーブルを関連付ける。
これは**応答を返す経路のため**であって、入口を開けるためではない。

## 3. よくある誤解

ネット上や生成 AI の説明には、次のような記述が混ざっていることがある。

| 誤り | 正しくは |
| --- | --- |
| IGW は、宛先のプライベート IP が属するサブネットのルートテーブルを確認し、`0.0.0.0/0 -> igw` がなければ「パブリックサブネットではない」と判断して入口で破棄する | そのような動作は AWS のドキュメントにない。行きは `local` で届き、止まるのは帰り。「パブリックサブネット」は IGW が判定する属性ではなく、「IGW へのルートを持つルートテーブルが関連付けられたサブネット」という呼び名にすぎない |
| `local` ルートは VPC 内から発信した通信にしか適用されず、外から入った通信には効かない | IGW から VPC に入った通信も、VPC 内の宛先へは `local` で届けられる。入口側の経路を変えるのは Ingress Routing で、明示的に設定したときだけ |

「結局つながらない」という結論は合っているので、誤りに気づきにくい。
違いが出るのは UDP のような片道で意味を持つ通信と、`tcpdump` で観察したとき(7 節)。

## 4. UDP ならプライベートのリソースに届くか

UDP は応答を必要としないので、「帰りがなくても、行きだけで何かを起こせるのでは」という疑問が出る。
答えは、パブリック IP の有無で分かれる。

| 状況 | 外からの UDP |
| --- | --- |
| パブリック IP なし(このリポジトリのプライベートサブネットのリソース) | 宛先として指定できないので**届かない** |
| パブリック IP あり + IGW へのルートなし | セキュリティグループが許可していれば**片道は届く**(応答は返らない) |
| パブリック IP あり + IGW へのルートあり | セキュリティグループが許可していれば往復できる |

2 行目は、たとえば EIP を付けた EC2 を `0.0.0.0/0 -> NAT` のサブネットに置いた場合にあたる。
受け取ったアプリが、その 1 パケットだけで何かの処理をしてしまう可能性はある。

NAT Gateway は、内側から始まった通信の戻りしか通さない。
外からの新規の通信の入口にはならないので、プライベートサブネットに外から入る経路を作ることはない。

## 5. RDS と ElastiCache

### RDS の「パブリックアクセス」(`PubliclyAccessible`)

この設定は、ファイアウォールのような「通信を許可するかどうか」のスイッチではない。
**DB インスタンスの ENI にパブリック IP を付けるかどうか**の設定である。

| 設定 | ENI のパブリック IP | エンドポイントの DNS が返す IP |
| --- | --- | --- |
| オフ | なし | 常にプライベート IP |
| オン | あり | VPC の外から引くとパブリック IP、VPC の中から引くとプライベート IP |

エンドポイントの DNS 名(`xxx.rds.amazonaws.com`)は、オフでもインターネットの DNS から引ける。
しかし返ってくるのがプライベート IP なので、外からその宛先に届く経路はない。
「DNS が引ける = パブリック IP を持っている」ではない。

オンにしても、外から実際につながるには次の条件もそろう必要がある。

- DB サブネットグループのサブネットに `0.0.0.0/0 -> igw` のルートがある(帰りの経路。2 節と同じ理屈)
- セキュリティグループが接続元を許可している

### ElastiCache

ElastiCache には、パブリック IP を付ける設定そのものがない。ノードは VPC 内からしか到達できない作りになっている。

### セキュリティグループを全開放したら

`PubliclyAccessible` がオフの RDS や ElastiCache で、セキュリティグループを全ポート・全プロトコル許可にした場合を考える。

- **インターネットから:** パブリック IP がないので、TCP でも UDP でも届かない(4 節の表の 1 行目)
- **VPC の中から:** 何でも届く。ECS タスクが乗っ取られたり、将来 VPC 内に別のリソースを置いたりすると、そこから DB の任意のポートを叩ける

「パブリック IP がない」と「セキュリティグループで接続元を絞る」は別々の防御の層である。
片方が崩れたときのために両方を効かせておく(多層防御)のが定石。

外からタスクに届く経路は ALB 経由だけになっている。

### プライベートのルートテーブルを AZ ごとに分けている理由

NAT が 1 台でも分けておくのは、prod で NAT を AZ ごとに置くとき、ルートの向き先を変えるだけで済むようにするためである。
ルートテーブルが 1 つだと、`0.0.0.0/0` の向き先は 1 か所しか指定できない。

冗長化するときの作業は次の 2 つ。

1. `NatGatewayEip` と `NatGateway` をもう 1 組作り、`PublicSubnetC` に置く
2. `PrivateDefaultRouteC` の `NatGatewayId` を新しい NAT に変える

AZ ごとに NAT を使わせると、次の利点がある。

- 1 つの AZ の障害で、もう片方の AZ のタスクが外に出られなくなることがない
- AZ をまたぐデータ転送料がかからない

ルートテーブル自体は無料。

### コンソールのリソースマップで見えるもの

- **名前のない `rtb-xxxxxxxx`:** VPC を作ると自動で作られるメインルートテーブル
  - 中身は `local` ルートだけ
  - このテンプレートでは 4 つのサブネットすべてに明示的な関連付け(`SubnetRouteTableAssociation`)があるので、どのサブネットからも使われない
  - タグが付かないのは、テンプレートの外で作られるため
  - VPC と一緒に消える
- **`-c` のサブネットが ap-northeast-1d にある:** AZ を `!Select [1, !GetAZs ""]` で取っているため。アカウントによっては 2 番目の AZ が 1c ではなく 1d になる。動作には問題ない

## 7. 確かめ方

3 節の誤りと正しい説明の違いは、実機で観察できるはず。

1. IGW へのルートがない(または NAT 向きの)サブネットに、パブリック IP 付きの EC2 を置く
2. セキュリティグループで、確かめたいポートを自分の IP から許可する
3. EC2 の中で `sudo tcpdump -n port <ポート>` を動かしながら、手元から接続する

正しい説明のとおりなら、`SYN` は届くのに `SYN-ACK` がクライアントに返らない様子が見える。
UDP なら、送ったパケットが EC2 に届くのが見える。
