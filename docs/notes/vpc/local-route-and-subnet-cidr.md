# ルートテーブルの `local` と CIDR の切り方

ルートテーブルの「送信先 `10.0.0.0/16`、ターゲット `local`」は何を意味するのか。
RDS への通信はどのルートを通るのか。VPC の CIDR はサブネットにどう切り分けるのか。
一般によく見る `10.0.0.0/16` と、このリポジトリの実際の値(stg の `192.168.0.0/20`)を並べて整理する。

続き → [VPC の入口と出口](inbound-routing-and-public-ip.md)(外からの通信はどこで止まるのか)

## まず結論(4 行)

- `local` ルートは「**VPC の範囲内の宛先へは、VPC の中で直接届ける**」というルール。VPC を作ると自動で入り、削除できない
- 宛先に当てはまるルートが複数あるときは、**範囲がいちばん狭いルート**が選ばれる(最長一致)。`local` だから優先されるわけではない
- VPC 内のリソース(RDS など)の名前解決で返るのはプライベート IP なので、その通信は `local` を通る。届くかどうかは、最後にセキュリティグループが決める
- サブネットは VPC の CIDR を重ならないように切り分けて作る。AWS は各サブネットで **5 個の IP を予約する**

## 1. ルートテーブルの読み方

ルートテーブルの 1 行は「**この範囲の宛先へ送るパケットは、ここに渡す**」という意味である。

| 列 | 意味 |
| --- | --- |
| 送信先(Destination) | 宛先 IP の範囲(CIDR) |
| ターゲット(Target) | その範囲宛てのパケットを渡す先(`local`、IGW、NAT Gateway、VPC エンドポイントなど) |

このリポジトリのプライベートサブネット(`private-rt-a`)のルートテーブルは、stg では次のようになる。

| 送信先 | ターゲット | 意味 |
| --- | --- | --- |
| `192.168.0.0/20` | `local` | VPC 内の宛先へは直接届ける |
| `pl-xxxxxxxx`(S3 のプレフィックスリスト) | `vpce-xxxxxxxx`(S3 ゲートウェイエンドポイント) | S3 の IP 範囲宛ては、エンドポイントに渡す |
| `0.0.0.0/0` | `nat-xxxxxxxx` | それ以外はすべて NAT Gateway に渡す |

一般的な `10.0.0.0/16` の VPC なら、1 行目が `10.0.0.0/16 → local` になるだけで、意味は同じ。

### `local` ルート

| | 一般的な例 | このリポジトリ(stg) |
| --- | --- | --- |
| ルート | `10.0.0.0/16 → local` | `192.168.0.0/20 → local` |
| 対象の範囲 | `10.0.0.0 〜 10.0.255.255` | `192.168.0.0 〜 192.168.15.255` |

- VPC を作ると、すべてのルートテーブルに自動で入る
- 削除はできない
- VPC 内のサブネット同士の通信と、サブネット内の通信は、すべてこのルートで届く

**「何があっても必ず直接届く」わけではない。** 2021 年から、`local` より狭い範囲のルートを追加できるようになった。
たとえば `10.0.10.0/24 → ファイアウォール用アプライアンス` のようにして、VPC 内の通信をわざと経由させられる。
このリポジトリでは使っていない。

## 2. どのルートが選ばれるか — 最長一致

宛先に当てはまるルートが複数あるときは、**プレフィックス長がいちばん長い(範囲がいちばん狭い)ルート**が選ばれる。
これを最長一致(longest prefix match)という。

| 宛先 IP | 当てはまるルート | 選ばれるルート |
| --- | --- | --- |
| `10.0.10.15`(一般的な例) | `10.0.0.0/16 → local`、`0.0.0.0/0 → NAT` | `/16` のほうが狭いので **`local`** |
| `192.168.2.15`(このリポジトリ) | `192.168.0.0/20 → local`、`0.0.0.0/0 → NAT` | `/20` のほうが狭いので **`local`** |
| `203.0.113.5`(インターネット上) | `0.0.0.0/0 → NAT` だけ | **NAT** |

`0.0.0.0/0` はすべてのアドレスに当てはまるが、範囲がいちばん広い(`/0`)ので、ほかに当てはまるルートがあれば必ず負ける。
「その他すべて」を受け持つので、デフォルトルートと呼ばれる。

## 3. RDS への通信の流れ

ECS タスクが RDS(Aurora)に接続するときの流れ。

1. タスクが RDS のエンドポイント(`xxx.rds.amazonaws.com`)を名前解決する
2. DNS が RDS の**プライベート IP** を返す(例: `10.0.10.15` / このリポジトリなら `192.168.1.x` か `192.168.2.x`)
3. タスクがその IP 宛てにパケットを送る
4. タスクがいるサブネットのルートテーブルで、宛先が `local` の範囲に入るので、VPC の中で直接 RDS に届く
5. **RDS のセキュリティグループ**が、送信元(ECS のセキュリティグループ)からの TCP 3306 を許可しているので、受け付けられる

補足が 3 つある。

- **プライベートな RDS の名前解決で、パブリック IP が返ることはない。** `PubliclyAccessible` をオンにした RDS でも、VPC の中から引けばプライベート IP が返る。詳しくは [VPC の入口と出口 5 節](inbound-routing-and-public-ip.md#5-rds-と-elasticache)
- **ルートテーブルは経路を決めるだけで、通すかどうかは決めない。** 手順 4 で経路が見つかっても、手順 5 でセキュリティグループ(と NACL)が拒否すれば届かない
- **宛先は IP アドレスで、プレフィックス長は付かない。** 「`10.0.1.1/20` 宛てに送る」という言い方はしない。`/20` はサブネットや VPC の「範囲」を表すときに付けるもの

## 4. CIDR の切り方

### VPC の CIDR は全体の枠

| | 一般的な例 | このリポジトリ(stg) |
| --- | --- | --- |
| VPC の CIDR | `10.0.0.0/16` | `192.168.0.0/20` |
| 範囲 | `10.0.0.0 〜 10.0.255.255` | `192.168.0.0 〜 192.168.15.255` |
| アドレスの数 | 65,536 個 | 4,096 個 |
| `/24` のサブネットを最大いくつ作れるか | 256 個 | 16 個 |

プレフィックス長が 1 減るとアドレスは 2 倍になる。`/24` は 256 個、`/20` は 4,096 個、`/16` は 65,536 個。

### サブネットは枠を重ならないように切り分ける

`/24` で切った場合。

| サブネット | 一般的な例 | このリポジトリ(stg) | 置くもの(このリポジトリ) |
| --- | --- | --- | --- |
| パブリック A | `10.0.1.0/24` | `192.168.3.0/24` | ALB、NAT Gateway |
| パブリック C | `10.0.2.0/24` | `192.168.4.0/24` | ALB |
| プライベート A | `10.0.10.0/24` | `192.168.1.0/24` | ECS タスク、Aurora、ElastiCache |
| プライベート C | `10.0.20.0/24` | `192.168.2.0/24` | ECS タスク、Aurora、ElastiCache |

大量の IP を使う環境では、`10.0.0.0/20`(`10.0.0.0 〜 10.0.15.255`)、`10.0.16.0/20`、…のように、サブネットを大きく切ることもある。
どう切っても、VPC の CIDR の内側に収まっていれば、`local` ルートで相互に通信できる。

### 各サブネットで 5 個の IP が予約される

`/24` のサブネットを例にすると、次の 5 個はリソースに割り当てられない。

| アドレス | 用途 |
| --- | --- |
| `.0` | ネットワークアドレス |
| `.1` | VPC ルーター |
| `.2` | DNS(Amazon が提供する DNS サーバー) |
| `.3` | 将来の利用のため予約 |
| `.255` | ブロードキャストアドレス(VPC はブロードキャストを使わないが予約される) |

| | サブネットの範囲 | 実際に割り当てられる範囲 | 数 |
| --- | --- | --- | --- |
| 一般的な例 | `10.0.1.0 〜 10.0.1.255` | `10.0.1.4 〜 10.0.1.254` | 251 個 |
| このリポジトリ(stg のパブリック A) | `192.168.3.0 〜 192.168.3.255` | `192.168.3.4 〜 192.168.3.254` | 251 個 |

「サブネットの範囲」と「割り当てられる範囲」は別物である。表や資料ではこの 2 つが混同されていることがあるので注意。

## 5. このリポジトリの値

| | stg([stg.json](../../../cloudformation/params/stg.json)) | prod([prod.json](../../../cloudformation/params/prod.json)) |
| --- | --- | --- |
| VPC | `192.168.0.0/20` | `192.168.16.0/20` |
| プライベート A | `192.168.1.0/24` | `192.168.17.0/24` |
| プライベート C | `192.168.2.0/24` | `192.168.18.0/24` |
| パブリック A | `192.168.3.0/24` | `192.168.19.0/24` |
| パブリック C | `192.168.4.0/24` | `192.168.20.0/24` |

`/20` の VPC を `/24` で切っているので、最大 16 個のサブネットのうち 4 個を使っている。
パラメータの定義は [app.yml:96-110](../../../cloudformation/app.yml#L96-L110)。

### stg と prod の範囲をずらしている理由

**範囲が重なる VPC を作ること自体はできる。** 同じアカウントやリージョンに `192.168.0.0/20` の VPC が 2 つあっても、作成は失敗しない。

重なっていて困るのは、**VPC 同士を接続するとき**である。
VPC ピアリング、Transit Gateway、VPN などでつなぐと、同じアドレスがどちらの VPC を指すのか決められず、ルートが作れない。
接続には CIDR が重ならないことが前提になる。

このリポジトリには今のところ VPC 同士の接続はない。
stg と prod をずらしているのは、将来つなぐことになっても衝突しないようにするためである。

## 6. よくある誤解

ネット上や生成 AI の説明には、次のような記述が混ざっていることがある。

| 誤り | 正しくは |
| --- | --- |
| `local` ルートは削除も変更もできない | 削除はできない。ただし、`local` より狭い範囲のルートを追加して、VPC 内の通信を別の経路に回せる(1 節) |
| `local` が優先的に評価される | 選ばれる理由は最長一致。`local` の範囲が `0.0.0.0/0` より狭いから選ばれる(2 節) |
| ルートテーブルに `local` があれば、VPC 内の相手に必ず届く | 経路が決まるだけ。届くかはセキュリティグループと NACL が決める(3 節) |
| `/24` のサブネットで「利用可能な範囲」は `.0 〜 .255` | `.0 〜 .255` はサブネットの範囲。割り当てられるのは `.4 〜 .254` の 251 個(4 節) |
| プライベートな RDS の名前解決ではパブリック IP が返る | プライベート IP が返る(3 節) |
| 範囲が重なる VPC は作れない | 作れる。重なると困るのは VPC 同士を接続するとき(5 節) |
