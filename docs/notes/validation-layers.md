# バリデーションの多層防御 — 文字数上限をアプリ側と DB 側のどちらで守るか

投稿本文の 280 文字上限が、なぜ**アプリ側と DB 側の両方**に書いてあるのか。「二重で無駄では?」「上限を変えるとき両方直すのは面倒では?」「その ALTER は重くないのか?」「DB 側には制限をかけずアプリ側だけ、はアリなのか?」という一連の疑問に答える学習メモ。PHP / Laravel 出身者向け。

## 結論 — 「両方に置く」が定石。しかも実は 3 層ある

同じ制限を複数の層に重ねて置くのは無駄ではなく、**多層防御(defense in depth)**と呼ばれる意図的な設計。それぞれの層は**役割が違う**ので、同じことの繰り返しにはならない。

そして、このプロジェクトの 280 文字はよく見ると **3 箇所**に存在する。元の「アプリ側(`@Column`)と DB 側で二重にかけている」という理解は half-right で、正確には次の 3 層に分かれている。

| 層 | 場所 | 正体 | 実行時に 281 文字を弾くか |
|---|---|---|---|
| ① アプリ側バリデーション | `CreatePostRequest.java:9` の `@Size(max = 280)` | Bean Validation(入力チェック) | **弾く**。DB に触る前に 400 を返す |
| ② JPA マッピング情報 | `Post.java:44` の `@Column(length = 280)` | エンティティ ↔ テーブルの対応表 | **弾かない**(後述) |
| ③ DB 制約 | `V1__create_base_tables.sql:35` の `VARCHAR(280)` | テーブル定義そのもの | **弾く**。最後の砦 |

「アプリ側で弾いている」のは ② ではなく ① の `@Size`。ここを取り違えると「なぜ 2 箇所(実は 3 箇所)あるのか」がうまく説明できないので、まずこの区別から入る。

## なぜ両方(複数)に置くのか — 役割が違うから

①〜③ は「念のための重複」ではなく、守っている対象と守り方が違う。

| 層 | 主な役割 | たとえるなら |
|---|---|---|
| ① `@Size`(アプリ側) | **使い勝手**。281 文字目を即座に弾き、「本文は 280 文字以内で入力してください」という**人間向けメッセージ**を返す。無駄な DB アクセスを未然に防ぐ | お店の**入口の受付**。ダメなものは入口で丁寧にお断りする |
| ③ `VARCHAR(280)`(DB 側) | **データの正しさの最終保証**。どんな経路から書き込まれても 281 文字は物理的に入らないと保証する | **金庫そのもの**。受付をすり抜けても金庫が受け付けない |

ここが本質。**アプリ側(①)のチェックだけだと「そのアプリのその入口を通ったデータ」しか守れない。** 実務では 1 つの DB に対して入口が複数できるのが普通で、たとえば次のような経路はすべて ① を通らない。

- 別のサービス / バッチ処理から直接書き込む
- 障害対応中に人間が手で `INSERT` する
- 将来追加する管理画面や別 API

これらすべてに ① を漏れなく実装し続けるのは現実的でない。だから **DB 自身にも制約を持たせて「最後の砦」にする**。これが多層防御。

逆に「③ だけ」で ① を省くと、ユーザーは入力中ではなく**送信して DB に弾かれて初めて**エラーに気づく。しかも DB が返すエラーは機械的でそのままユーザーに見せられない。だから **UX のために ① も置く**。つまり「両方あるのは面倒」というデメリットは、**安全と UX を両取りするための意図的なコスト**。

### ② `@Column(length = 280)` は何のためにあるのか

②は「実行時に入力を弾く」層ではない。JPA(Hibernate)における `@Column(length)` は、本来 **エンティティからテーブルを自動生成(DDL 生成)するときの「この列は VARCHAR(280) で作れ」という指示**であって、`save()` 時に本文の長さを検査するものではない。仮に ① の `@Size` が無ければ、300 文字の本文は ② を素通りして DB(③)に弾かれる。

このプロジェクトはスキーマを **Flyway で管理**し、Hibernate には `ddl-auto: validate`(自動生成はせず、起動時に突き合わせるだけ)を設定している(→ [flyway-basics.md](./flyway-basics.md))。そのため ② が DDL を生成することはない。では飾りかというとそうではなく、**起動時のスキーマ検証に使われる**。`validate` はエンティティのマッピングと実テーブルを突き合わせ、食い違うと起動時に例外を投げる。したがって ② は「**この列は 280 という宣言をコード側にも残し、③ とズレたら起動時に気づけるようにする**」ための存在。

> ⚠️ ただし Hibernate が VARCHAR の**長さ**まで厳密に検証するかは、Hibernate のバージョンや DB 方言によって挙動が揺れる部分([参考: Vlad Mihalcea](https://vladmihalcea.com/how-to-fix-wrong-column-type-encountered-schema-validation-errors-with-jpa-and-hibernate/))。「② を直さなければ必ず起動失敗する」と断定はできない。だから ② を検証の頼みにするのではなく、**運用ルールとして 3 層を常に同期させる**のが正解(後述)。

### Laravel だとどうなるか

多層防御の発想は Laravel でもまったく同じ。対応関係はこうなる。

| このプロジェクト(Java) | Laravel | 役割 |
|---|---|---|
| ① `@Size(max = 280)`(FormRequest 相当の DTO) | FormRequest の `'body' => 'max:280'` | アプリ側の入力バリデーション |
| ② `@Column(length = 280)` | **相当なし** | JPA 特有。Eloquent はモデルに列長を宣言しない |
| ③ `VARCHAR(280)` | migration の `$table->string('body', 280)` | DB 制約 |

Laravel で「バリデーションルール(`max:280`)と migration の列長を両方書く」のと、ここで「`@Size` と `VARCHAR` を両方書く」のは同じこと。**②(`@Column(length)`)だけが Java 特有**で、「Eloquent には無い中間層があるんだな」と捉えると理解しやすい。

## このプロジェクトでの実際の流れ

投稿作成(`POST /api/posts`)で ① がどう発動するか、コードで追うとこうなる。

```
ブラウザ(JSON: {"body": "…281文字…", "categoryId": 1})
   ↓
PostController.create(@Valid @RequestBody CreatePostRequest request)   … @Valid が検証を起動
   ↓ @Size(max=280) 違反
MethodArgumentNotValidException が投げられる(PostService には到達しない)
   ↓
GlobalExceptionHandler.handleValidation() が捕捉      … GlobalExceptionHandler.java:36
   ↓
HTTP 400 + {"message":"入力内容に誤りがあります","fieldErrors":{"body":"本文は280文字以内で入力してください"}}
```

- 起動役は `PostController` の `create` に付いた `@Valid`(`@RequestBody` の中身を検証せよという指示)。
- 弾かれた本文は `PostService.create`(`PostService.java:84`)にすら渡らない。だから DB アクセスは一切発生しない = ① が「無駄な DB アクセスを防ぐ」と言えるのはこのため。
- 変換は各 Controller ではなく共通の `GlobalExceptionHandler`(`@RestControllerAdvice`)が一手に引き受ける。`@Size` の `message` に書いた文字列がそのままフィールド別エラーになる。

なお同じ発想で、クエリパラメータ側にも `@Min(1) @Max(50)`(`PostController` の `timeline` の `limit`)というアプリ側バリデーションがあり、こちらは `ConstraintViolationException` として `GlobalExceptionHandler.java:46` が 400 に変換する。

## 上限を変えるとき、何箇所直すのか — DRY 違反ではない

「上限を上げるたびに複数箇所を直すのは、DRY(繰り返しを避ける原則)に反して気持ち悪い」という感覚は正しい。ただし整理すると、**①〜③ は「同じことの繰り返し」ではなく「役割の違う三重化」**なので、ここは重複させるのが正解。

上限を 280 → 500 にするなら、直すべきは:

1. ③ DB … `ALTER TABLE posts MODIFY body VARCHAR(500) NOT NULL;`(新しい Flyway の V ファイルとして追加。適用済みファイルは編集しない → [flyway-basics.md](./flyway-basics.md))
2. ① `@Size(max = 500)` … これを直さないと、DB は 500 まで許すのにアプリが 280 で弾き続ける
3. ② `@Column(length = 500)` … 起動時スキーマ検証と「コード上の宣言」を ③ に揃えるため

「アプリ側のコード内の重複」(たとえば同じ `280` を複数のバリデーションから参照する)は、`private static final int BODY_MAX = 280;` のような定数にまとめて減らせる。ただし **DB の DDL とアプリのコードは仕組み上どうしても別管理**になる(SQL と Java は別ファイル・別ビルド)。この層をまたぐ二重定義だけは「多層防御のための必要コスト」と割り切るのが実務的な落としどころ。

## その ALTER は重いのか — INPLACE と COPY、255 バイトの壁

「VARCHAR を広げる ALTER は重い(テーブルロックして全行コピー)のでは?」という心配。結論は **今回のケースなら軽い**。ただし「軽くなる条件」があるので、そこを理解しておく。

MySQL 8 の `ALTER TABLE` には 2 つの実行方式がある。

- **COPY** … テーブルを丸ごと作り直し、全行をコピーし直す。行数が多いほど遅い。**重い。**
- **INPLACE** … メタデータ中心の書き換えで済み、行のフルコピーが要らない。**軽い**(Online DDL)。

VARCHAR の拡張が INPLACE で済むかどうかは、公式ドキュメントに明確なルールがある([MySQL 8.0 Online DDL Operations](https://dev.mysql.com/doc/refman/8.0/en/innodb-online-ddl-operations.html))。VARCHAR は各値の先頭に「文字列の長さ」を記録する**長さプレフィックス**という小領域を持っており、そのバイト数が変わるかどうかが分岐点になる。

- 格納最大バイト数が **0〜255 バイト** → 長さプレフィックスは **1 バイト**
- 格納最大バイト数が **256 バイト以上** → 長さプレフィックスは **2 バイト**

> **INPLACE(軽い)で済む条件**: 拡張の前後で長さプレフィックスのバイト数が変わらない。
> **COPY(重い)になる条件**: 255 バイト以下 → 256 バイト以上 の境界をまたぐ(1 バイト → 2 バイトに変わる)。

ここで**文字コード**が効く。`posts` テーブルは `CHARSET = utf8mb4`(`V1__create_base_tables.sql:40`)で、utf8mb4 は **1 文字最大 4 バイト**。だから:

- `VARCHAR(280)` の最大格納バイト数 = 280 × 4 = **1120 バイト**(すでに 256 以上 → **2 バイトプレフィックス**)
- `VARCHAR(500)` に拡張 = 500 × 4 = **2000 バイト**(これも 256 以上 → **2 バイトプレフィックス**)

**プレフィックスのバイト数が変わらない → INPLACE = 軽い**。数百万行あっても行のフルコピーは起きない。「重い SQL になるのでは?」は今回に関しては杞憂。

念のため方式を明示し、COPY にしかできないならエラーで止める書き方もできる:

```sql
ALTER TABLE posts MODIFY body VARCHAR(500) NOT NULL, ALGORITHM=INPLACE, LOCK=NONE;
```

⚠️ **逆に重くなる例**もある。utf8mb4 で `VARCHAR(63)`(= 252 バイト、1 バイト)を `VARCHAR(64)`(= 256 バイト、2 バイト)に広げると、255 バイトの境界をまたぐので **COPY = 重い**。「VARCHAR を広げるのは常に軽い」ではなく「**255 バイトの壁をまたがなければ軽い**」が正確な理解。

## DB 側に制限をかけず、アプリ側だけにする実装

これも実在する。代表的なのはカラム型を **`TEXT` 系**にすること。

```sql
body TEXT NOT NULL   -- DB 側は長さ無制限(実質 65535 バイト)。文字数チェックは ① の @Size だけで行う
```

こうすると上限を変えたいとき **DDL(ALTER)を打たず、① の `@Size` を書き換えるだけ**で済む。「複数箇所を直す面倒」を解消する方向の実装で、上限が頻繁に変わる・上限自体が曖昧、といった要件では採られることもある。ただし引き換えに失うものがある。

| 観点 | 現状(③ に `VARCHAR` を置く) | アプリ側だけ(③ を `TEXT` に) |
|---|---|---|
| データ整合性の保証 | ◎ どの経路から書いても 281 文字は絶対入らない | △ アプリのバグ・別経路で長い文字列が混入する余地が残る |
| 上限変更の手間 | △ 複数箇所(ただし ALTER は軽い) | ◎ アプリ側だけ |
| ストレージ / インデックス | ◎ VARCHAR は行内に収まりやすく素直。INDEX も付けやすい | △ TEXT は行外格納になりやすく、INDEX に長さ(接頭辞)指定が要るなどクセがある |
| 仕様がスキーマから読めるか | ◎ `VARCHAR(280)` を見れば一目 | △ スキーマからは分からず、アプリのコードを読む必要がある |

**この掲示板系の 280 字投稿なら、現状(③ に `VARCHAR(280)` を置く多層防御)がベストプラクティス**。理由は (1) 280 は「そういう仕様」で頻繁には変わらない、(2) 変えても utf8mb4 × 280 起点の拡張は INPLACE で軽い、(3) ユーザー入力を無制限に受けたくない列なので DB に最後の砦を置く価値が高い、の 3 点。

## つまずきポイント

- **「アプリ側の制御 = `@Column(length)`」は誤解。** 入力を実行時に弾くのは `@Size`(①)。`@Column(length)`(②)は DDL 生成用 + スキーマ検証用のマッピング情報で、`save()` 時に長さを検査しない。
- **`@Size` を消すと DB 任せになる。** ① を消してもコンパイルは通り、280 字以内なら動く。だが 281 字を送ると 400 の親切なエラーではなく、DB エラー起因の 500 相当になり UX が壊れる。「動くけど守れていない」典型。
- **VARCHAR 拡張が常に軽いと思い込む。** 255 バイトの壁をまたぐと COPY になり重い。utf8mb4 は 1 文字 4 バイト換算なので、「文字数」ではなく「文字数 × 4 バイト」で 256 の境界を判断する。
- **ALTER は Flyway の新しい V ファイルで。** 適用済みの `V1` を直すと checksum mismatch で起動失敗する(→ [flyway-basics.md](./flyway-basics.md))。上限変更は `V3__widen_post_body.sql` のように前進で足す。
- **3 層の同期を忘れる。** DB だけ広げて `@Size` を直し忘れると、DB は許すのにアプリが弾き続ける(逆も然り)。上限変更はセットで行う。

## 用語集

- **バリデーション** — 入力値が要件(必須・文字数など)を満たすか検査すること。ここでは「アプリ側バリデーション(①)」を主に指す
- **多層防御(defense in depth)** — 同じ目的の防御を、役割の違う複数の層に重ねる設計。1 つの層をすり抜けても次で守る
- **Bean Validation** — Java 標準の入力検証の仕組み。`@Size` / `@NotBlank` / `@Min` などのアノテーションで宣言する(`jakarta.validation.constraints.*`)
- **`@Valid`** — 受け取ったオブジェクトの中身を Bean Validation で検証せよ、という指示。これが無いと `@Size` 等は発動しない
- **DTO(Data Transfer Object)** — 層をまたいでデータを運ぶ入れ物。ここでは受信用の `CreatePostRequest`
- **`@Column(length)`** — JPA のマッピング情報。DDL 生成時の列長指定 + スキーマ検証に使われる。実行時の入力検査ではない
- **`ddl-auto: validate`** — Hibernate に「スキーマは自動生成せず、エンティティと実テーブルの一致を起動時に検証するだけ」とさせる設定
- **DDL / DML** — DDL は構造を変える SQL(`CREATE` / `ALTER`)、DML はデータを操作する SQL(`INSERT` / `UPDATE`)。`ALTER` は DDL
- **Online DDL** — テーブルを(ほぼ)ロックせず使いながらスキーマ変更できる MySQL の仕組み。`ALGORITHM=INPLACE` + `LOCK=NONE` が代表
- **INPLACE / COPY** — `ALTER TABLE` の実行方式。INPLACE は行をコピーせず軽い、COPY はテーブルを作り直すため重い
- **長さプレフィックス** — VARCHAR が各値の先頭に持つ「長さ」記録領域。255 バイト以下なら 1 バイト、256 バイト以上なら 2 バイト。これが変わると COPY になる
- **utf8mb4** — MySQL の文字コード。1 文字最大 4 バイト。絵文字も扱える。バイト数換算は「文字数 × 4」
