# docker exec とシェル — bash / sh はいつ必要で、何をしているのか

「`docker compose exec nuxt npm install` は sh なしで動くのに、`sh ./gradlew build` や `bash` を付けることもある。いつ必要なの?」という疑問と、その根っこにある「exec はコマンドをシェルに打ち込んでいるのではない」という仕組みの話。

## 大前提: コンテナの中にシェルは常駐していない

「コンテナの中には(自分の PC のターミナルのように)シェルが待ち構えていて、docker exec はコマンド文字列をそこに届けて打ち込んでくれる」——このイメージが誤解の根っこ。コンテナは小さなパソコンではなく**ただのプロセスの集まり**で、ログイン画面もターミナルもシェルもない。

backend コンテナで実測した全プロセス一覧:

```
PID 1:   java      ← bootRun で起動したアプリ
PID 41:  java      ← Gradle 関連
PID 144: java      ← 〃
PID 381: sh        ← この観測コマンド自体を動かすために exec で起動した分
```

普段いるのは java だけ。「コマンドを受け取って解釈してくれる係」はどこにもいない。

## exec は「文字列をシェルに渡す」のではなく「配列を OS に渡す」

「与えられたコマンドをそのままコンテナ内に渡している」は正しい。ただし**「そのまま」= 配列のまま、解釈なしで**、という意味。普段のターミナルと比べると:

```
【普段のターミナル】
  "npm install && npm run dev" という 1 本の文字列
    → bash が読んで解釈(単語に分割、&& の意味を処理)
    → プログラムを起動

【docker compose exec nuxt npm install】
  ["npm", "install"] という引数の配列
    → デーモンに配列のまま届く
    → コンテナ内で OS に「npm をこの引数で起動して」と直接依頼
  ※ 文字列を読み直して解釈する係はどこにもいない
```

だから `docker compose exec nuxt npm install "&&" npm run dev` と無理やり渡しても、`&&` は「連結して実行しろ」という命令にならず、npm への**ただの文字列引数**として届く。`&&` を命令として理解できるのはシェルだけ。

Dockerfile の exec 形式 CMD(`["npm", "run", "dev"]`)が配列で書くのも同じ理由([docker-dev-containers.md](./docker-dev-containers.md))。あれは「シェルに読ませる文字列」ではなく「OS に渡す引数の配列」を直接書いている。

## bash / sh が必要になる 3 つの場面

「1 個のプログラム + その引数」で表せるコマンドならシェル不要(`npm install` はまさにこれ)。必要なのは:

1. **シェルの「文法」を使いたいとき** — `&&` 連結、`|` パイプ、`>` リダイレクト、`*` ワイルドカード、`$変数`、until ループなど。これらはプログラムではなく**シェルという言語の文法**なので、解釈者(シェル)を先に起動して文字列を読ませる
2. **実行権限がないスクリプトファイルを動かすとき** — `sh ./gradlew`(実行権限の保険 → [docker-dev-containers.md](./docker-dev-containers.md))
3. **対話シェルとして中に入りたいとき** — `docker compose exec backend bash`。実行したいプログラムがたまたまシェルというだけ

sh の使い方 3 通りがこの 3 場面に対応する:

| 書き方 | 意味 | 場面 |
|---|---|---|
| `sh -c "文字列"` | 文字列をシェル文法として解釈・実行 | ① 文法を使う |
| `sh ファイル` | ファイルを台本として読んで実行 | ② 実行権限の保険 |
| `sh`(引数なし) | 対話モードで起動し、入力を待つ | ③ 中に入る |

### このリポジトリの実例

- **① の実物**: minio-init の `entrypoint: sh -c "until ...; do sleep 1; done; mc mb ..."`(docker-compose.yml)。リトライループ + 複数ステップなのでシェル文法が必須
- **② の実物**: backend の CMD `["sh", "./gradlew", "bootRun"]`(docker/backend/Dockerfile)
- **シェル不要の実物**: mysql のヘルスチェック `["CMD", "mysqladmin", "ping", ...]`(docker-compose.yml)。1 プログラム + 引数で足りるから直接起動

## exec は両方ともコマンド指定が必須

「`docker exec` は bash/sh 不要で、`docker compose exec` だけ必要」という理解は誤り。**どちらも「何を実行するか」の指定が必須**で、省略するとどちらも同じ趣旨のエラーになる(実測):

```
$ docker compose exec backend
requires at least 2 arg(s), only received 1

$ docker exec nuxt-java-practice-backend-1
"docker exec" requires at least 2 arguments
```

2 つのコマンドの違いは「名前の指定方法(コンテナ名かサービス名か)」だけ([docker-container-names.md](./docker-container-names.md))。混同しやすい隣人が 2 ついる:

- **`docker run`** はコマンド省略可(イメージの CMD がデフォルトとして使われる)。exec にはデフォルトのコマンドという概念自体がない
- **`-it` フラグ** — exec の必須オプションではなく**対話専用の道具**。`docker exec <名前> ls` のような 1 回きりのコマンドには不要(実測)。必要なのはシェルに入って対話するときで、`-i` が手元の入力をコンテナ内のプログラムに繋ぎ、`-t` が「人間の端末と話している」と思わせる(プロンプト表示・矢印キー・Ctrl+C が効く)。`-it` なしで `bash` を起動すると、入力が繋がっていないため bash は「もう入力は来ない」と判断して**何も起きず即終了する**(実測)。`docker compose exec` は**デフォルトで両方 ON** なので付けなくてよい——「compose のほうが何か省略できる」という印象の出どころはおそらくここ。中間形態として `-i` だけ付けて `... | docker exec -i <名前> bash` とパイプで台本を流し込む使い方もある(SQL のリストア等)

## bash と sh の違い

- **sh** は「POSIX 標準シェル」という**役職名**で、実体は OS によって別のプログラム。このリポジトリの backend / nuxt コンテナでは `/bin/sh -> dash` というシンボリックリンクだった(実測)。dash は標準機能だけの小さく高速なシェル
- **bash** は sh の上位互換(Bourne Again SHell)。配列や `[[ ]]` などスクリプト向けの拡張と、タブ補完・履歴など対話向けの快適機能を持つ。backend / nuxt には `/usr/bin/bash` が入っていた(実測)
- 使い分けの目安: **スクリプトを動かすだけなら sh、対話で中に入るなら bash が快適**。軽量イメージ(Alpine 系など)には bash がいないことがあるが、sh はほぼ確実にいる。`bash` で入ろうとしてエラーになったら `sh` を試すのが定石

## 落とし穴: ホスト側のシェルが先に手を出してくる

exec の道中で唯一シェル解釈が入るのは、**ホストで打った瞬間**(ホストの bash が引数分割やワイルドカード展開をする)。

- `docker compose exec backend ls *.jar` — `*.jar` は**ホストの bash が**カレントフォルダで展開しようとする。コンテナ内で展開させたいなら `sh -c "ls *.jar"` と引用符で守って渡す
- `$変数` も同様で、`"$HOME"` は**ホストの値**に展開されてから渡る。コンテナ内の値が欲しいなら `sh -c 'echo $HOME'` と**シングルクォート**で(シングルクォートはホストの展開を止める)

## 用語集

- **シェルの文法** — `&&` / `|` / `>` / `*` / `$変数` / until など、プログラムではなくシェルが解釈する記号・構文
- **直接起動** — シェルの解釈を経ずに OS がプログラムを起動すること。exec のデフォルトの動き
- **`sh -c "文字列"`** — 文字列をシェル文法として解釈・実行させる書き方。複数コマンドを 1 コマンドに包む手段
- **対話モード** — シェルが入力を待ち続ける状態。「コンテナに入る」の正体
- **POSIX 標準シェル(sh)** — どの Unix 系 OS にもいる標準シェルという役職。実体は dash だったり busybox だったりする
- **dash** — Debian / Ubuntu 系の `/bin/sh` の実体。標準機能だけの小さく高速なシェル
- **bash** — sh の上位互換シェル。スクリプト拡張 + 対話向けの快適機能
- **`-it`** — 対話専用のフラグ(i = 入力を繋ぐ、t = 端末として振る舞う)。シェルに入るときだけ必要で、1 回きりのコマンド実行には不要。`docker compose exec` ではデフォルトなので常に不要
- **`docker run`** — イメージから新しいコンテナを作って起動するコマンド。CMD がデフォルトになるためコマンド省略可(exec との違い)
- **シングルクォート** — ホスト側シェルの変数展開・ワイルドカード展開を止める囲い。コンテナ内で解釈させたい文字列を守る
