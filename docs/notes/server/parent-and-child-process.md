# 親プロセスと子プロセス — プロセスは必ず別のプロセスから生まれる

「子プロセスとは何か? タスクマネージャーを見ても、あるプロセスの親がどれなのか分からない」という疑問に答える学習メモ。結論を先に言うと:

- **子プロセスは「あるプロセスが起動した、別のプロセス」。** 起動した側を親プロセスと呼ぶ。プロセスは必ず既にあるプロセスから作られるので、**すべてのプロセスに親がいる**(1 章)。
- **子は親とメモリを共有しない。** 別のプロセスだから。受け継ぐのは環境変数や実行ユーザーなど、起動時の設定の写しだけ。ここがスレッドとの違い(2 章)。
- **タスクマネージャーでは親子関係が見えない。** 「詳細」タブに親の PID の列が無い。Windows なら Process Explorer か PowerShell、Linux なら `ps -ef --forest` や `pstree` で見る(3 章)。
- **親が先に終わったときの扱いが、Linux と Windows で違う。** Linux では PID 1 が子を引き取る。Windows では誰も引き取らない(4 章)。

プロセスそのものとスレッドの話は → [process-and-thread.md](./process-and-thread.md)

## 0. どこで出てきたか

[process-and-thread.md](./process-and-thread.md) の 3 章で、開発用の `worker` コンテナに Java のプロセスが 3 つ、親子の関係で並んでいた。5 章では「子プロセスが落ちても ECS は気づかない」「親を失ったプロセスは PID 1 に引き取られる」という話が出た。ここから「そもそも子プロセスとは何か」「親はどこで確かめられるのか」という疑問が出た。

## 1. 子プロセスとは

**あるプロセスが OS に頼んで起動させた、別のプロセス**のこと。頼んだ側が**親プロセス**、起動された側が**子プロセス**である。

プロセスは、何もないところからは生まれない。必ず既にあるどれかのプロセスが「このプログラムを起動して」と OS に頼んで作られる。そのため、すべてのプロセスに親がいる。親の PID を **PPID** と呼ぶ。

身近な例:

| 親 | 子 | 何が起きているか |
|---|---|---|
| ターミナルのシェル(`bash`) | `ls` | `ls` と打つと、シェルが `ls` を子プロセスとして起動し、終わるのを待つ |
| エクスプローラー(`explorer.exe`) | ダブルクリックしたアプリ | Windows でアプリを起動すると、エクスプローラーが親になる |
| `gradlew` | Gradle デーモン → アプリ本体 | 開発用の `backend` / `worker` コンテナ。3 世代の親子(下の図) |
| Nginx の master | worker | master が worker を複数起動する(→ [process-models-by-server.md](./process-models-by-server.md)) |

開発用の `worker` コンテナを、もう一度見る。

```
$ docker compose exec worker ps -eo pid,ppid,args
    PID    PPID COMMAND
      1       0 java ... gradlew
     41       1 java ... (Gradle デーモン)
    140      41 java ... (アプリ本体)
    520       0 ps -eo pid,ppid,args
```

`PPID` の列を親の `PID` に結ぶと、1 本の木になる。

```
PID 1    gradlew
└─ PID 41   Gradle デーモン      (PPID 1   = gradlew の子)
   └─ PID 140  アプリ本体         (PPID 41  = Gradle デーモンの子)
```

最後の行の `ps` 自身は PPID が 0 になっている。`docker compose exec` で起動したプロセスの親は、コンテナの外にいる Docker のプロセスである。コンテナの中からは外のプロセスが見えないので、0 と表示される。PID 1 の PPID が 0 なのも同じ理由である。

### Linux 全体では 1 本の木

Linux では、OS が起動して最初に作るプロセス(`systemd`、PID 1)が、すべてのプロセスの根になる。`systemd` が `sshd` を起動し、`sshd` が SSH で入ってきた人のシェルを起動し、シェルが `ls` を起動する、というように、全プロセスが 1 本の木にぶら下がっている。

```
systemd(PID 1)
├─ sshd
│  └─ sshd(接続ごと)
│     └─ bash
│        └─ ls
└─ containerd
   └─ containerd-shim
      └─ java(コンテナの PID 1)
```

## 2. 子が親から受け継ぐもの、受け継がないもの

子プロセスは**別のプロセス**なので、メモリ空間は親とは別になる。親が持っているオブジェクトや変数を、子が直接読むことはできない。同じプロセスの中でメモリを共有する**スレッドとは、ここが違う**。

| | 子プロセス | スレッド |
|---|---|---|
| 作った側とメモリを共有するか | **しない** | する |
| 作った側が終わったら | 生き残れる(4 章) | プロセスごと終わる |
| PID | 自分の PID を持つ | 持たない(プロセスの PID に属する) |

子が親から受け継ぐのは、**起動したときの設定の写し**である。

| 受け継ぐもの | 補足 |
|---|---|
| 環境変数 | 親の環境変数の**写し**。子が書き換えても親には影響しない(→ [../env-vars-basics.md](../env-vars-basics.md)) |
| 実行ユーザー | 親と同じ権限で動く(→ [../os-users-and-file-locations.md](../os-users-and-file-locations.md)) |
| 作業ディレクトリ | 親がいたディレクトリから始まる |
| 標準入力・標準出力 | 親の画面やパイプにつながったまま。シェルから起動したコマンドの出力が、同じ画面に出るのはこのため |

コンテナでも同じで、`gradlew` に渡した環境変数(`APP_ROLE=worker` など)は、写しとして Gradle デーモン、アプリ本体へと受け継がれていく。

## 3. 親子関係の見方

### タスクマネージャーでは分からない

タスクマネージャーの「詳細」タブには、PID の列はあるが、**親の PID の列が無い**(「列の選択」にも無い)。

「プロセス」タブで Chrome などを展開すると、中身がまとまって見える。ただしこれは**アプリ単位のまとまり**で、親子関係そのものではない。

### 見る方法

| 環境 | 方法 | 見え方 |
|---|---|---|
| Windows | **Process Explorer**(Microsoft 公式の Sysinternals ツール。無料) | 親子が木の形で並ぶ。タスクマネージャーの代わりとしてよく使われる |
| Windows | PowerShell で `Get-CimInstance Win32_Process \| Select-Object ProcessId, ParentProcessId, Name` | `ParentProcessId` が親の PID |
| Linux | `ps -ef` | `PPID` の列が親の PID |
| Linux | `ps -ef --forest` / `pstree -p` | 親子を木の形で表示する |
| コンテナ | `docker compose exec <サービス> ps -eo pid,ppid,args` | コンテナの中の親子。外の親は 0 と表示される(1 章) |

## 4. 親が先に終わったとき

親が子より先に終わったとき、残された子の扱いが OS によって違う。

| | Linux | Windows |
|---|---|---|
| 残された子 | **PID 1 の子に付け替えられる**(PPID が 1 になる) | 誰にも付け替えられない。**消えた親の PID を記録したまま**動き続ける |
| 子が終わったとき | 新しい親(PID 1)が、終了を受け取って片付ける必要がある | 特に何も要らない |

Linux で、親を失った子を引き取ることを**再親子付け**(reparenting)と呼ぶ。引き取った PID 1 が子の終了を受け取らない(`wait` しない)と、終わった子の記録が**ゾンビプロセス**として残り続ける。普通の Linux では `systemd` が片付けてくれるが、コンテナの中では、PID 1 がアプリ本体(このリポジトリなら `java`)になる。アプリは片付けをしないので、ゾンビが溜まりうる。これが、ECS の `initProcessEnabled` で init プロセスを PID 1 に置く理由である(→ [process-and-thread.md](./process-and-thread.md) の 5 章)。

Windows では、記録された親の PID が、後から起動した**別のプロセスに使い回されている**ことがある。Windows で親子関係をたどるときは、親の PID が本当にその親かどうか、起動時刻も合わせて確かめる必要がある。Process Explorer は、親が既に終わっている子を木の根の側に表示する。

### 親が終わると子も止まる、とは限らない

親が終わっても、子は自動では止まらない(Linux・Windows とも)。ターミナルを閉じるとそこから起動したコマンドも止まるのは、親子だからではなく、ターミナルが閉じるときに子へ終了の合図(SIGHUP)を送っているからである。

同じように、コンテナの PID 1 に届いた SIGTERM は、子プロセスには自動では届かない。PID 1 が自分で子に伝える必要がある。シェルスクリプトから `exec` を付けずにアプリを起動すると、SIGTERM がアプリに届かないのはこのためである(→ [process-and-thread.md](./process-and-thread.md) の 5 章)。

## つまずきポイント

- **子プロセスを、スレッドと同じものだと思う。** 子プロセスは別のプロセスで、親とメモリを共有しない。受け継ぐのは起動時の設定の写しだけ(2 章)
- **タスクマネージャーの「プロセス」タブのまとまりを、親子関係だと思う。** あれはアプリ単位のまとまり。親子は Process Explorer や PowerShell で見る(3 章)
- **子が環境変数を書き換えれば、親にも伝わると思う。** 子が持っているのは写し。親には戻らない(2 章)
- **親が終われば子も終わると思う。** 子は自動では止まらない。ターミナルを閉じたときに止まるのは、ターミナルが合図を送っているから(4 章)
- **コンテナの中で PPID が 0 のプロセスを、親がいないプロセスだと思う。** 親はコンテナの外にいて、中から見えないだけ(1 章)
- **Windows で、PPID が指すプロセスを親だと信じ切る。** 親が終わった後、その PID が別のプロセスに使い回されていることがある(4 章)

## 用語集

- **親プロセス** — 別のプロセスを起動したプロセス
- **子プロセス** — 別のプロセスから起動されたプロセス。親とはメモリを共有しない
- **PPID** — 親プロセスの PID
- **プロセスツリー** — 親子関係でプロセスを結んだ木。Linux では `systemd`(PID 1)が根になる
- **再親子付け(reparenting)** — Linux で、親を失ったプロセスを PID 1 などが引き取ること
- **ゾンビプロセス** — 終了したのに、親がその終了を受け取らないため、記録だけが残っているプロセス
- **Process Explorer** — Microsoft の Sysinternals が配布する、プロセスを親子の木で表示するツール
- **`ps -ef --forest` / `pstree`** — Linux で、プロセスを親子の木の形で表示するコマンド
