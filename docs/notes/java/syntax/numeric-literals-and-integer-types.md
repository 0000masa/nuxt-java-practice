# 数値リテラルの型(1 と 1L) — 同じ「1」なのに型が違うとはどういうことか

`new CategoryResponse(1L, "お知らせ")` の `1L` は何なのか、DB には 1, 2, 3 という整数が入っているのになぜ Java では `1L` と書くのか、という疑問をまとめた学習メモ。結論を先に言うと、**`1L` の値は `1` とまったく同じ。`L` は値の一部ではなく「この 1 を long という大きさの箱で扱え」というコンパイラへの指示**。そして、この「リテラルに型を付ける」という発想は **整数型を複数持つ言語に固有のもの**で、PHP には存在せず、JavaScript / TypeScript には BigInt の `1n` という形で後から入った。

## 1L の値は 1 — まず確かめる

```java
System.out.println("1L == 1 -> " + (1L == 1));
```

```
1L == 1 -> true
```

`L` は数字に付く飾りでも、別の数を表す記号でもない。「1個」と書いても「1コ」と書いても数が 1 であることは変わらないのと同じで、`1` も `1L` も数としては 1。違うのは**入れ物のサイズだけ**。

## なぜ書き分けが要るのか — Java の整数型は 4 種類ある

| 型 | サイズ | 表せる最大値 |
|---|---|---|
| `byte` | 1 バイト | 127 |
| `short` | 2 バイト | 32,767 |
| **`int`** | 4 バイト | **2,147,483,647**(約 21 億) |
| **`long`** | 8 バイト | **9,223,372,036,854,775,807**(約 922 京) |

(下 2 つは `Integer.MAX_VALUE` / `Long.MAX_VALUE` を実行して確認した値)

そして Java には **「数字をそのまま書いたら `int` とみなす」というルール**がある。

```java
1     // Java はこれを int(4 バイトの箱)だと解釈する
1L    // L を付けると long(8 バイトの箱)だと解釈する
```

つまり `L` は「デフォルトの `int` ではなく `long` のほうで頼む」という指定。小数の世界で `1` と `1.0` を書き分けるのと同じ発想で、数はどちらも 1 だが型が違う。

> **小文字の `l` は使わない。** `1l` は数字の `1` と見分けが付かないため、大文字の `L` が慣習。小数側にも `f` / `d` というサフィックスがあるが、既定の型が整数とは逆向きになっている(→ 後述の「小数にもサフィックスがある」)。

## L を省くとコンパイルエラーになる

`CategoryResponse` の第 1 引数は `Long` 型(`CategoryResponse.java:5`)。ここに `L` なしの `1` を渡すとコンパイルが通らない。

```java
new CategoryResponse(1, "お知らせ");   // ✗ エラー
new CategoryResponse(1L, "お知らせ");  // ○
```

```
error: incompatible types: int cannot be converted to Long
```

値は同じ 1 なのになぜ弾かれるのか。**箱の種類が違い、Java は箱の詰め替えを 1 段までしか自動でやらない**ため。

```
1   →  int(4バイト)  →  long(8バイト)  →  Long(オブジェクト)
                     ↑ 拡大変換        ↑ ボックス化   ← 2 段は自動適用されない = エラー

1L  →  long(8バイト)  →  Long(オブジェクト)
                      ↑ ボックス化 1 段だけ         ← これは自動でやってくれる = OK
```

`L` を付けるのは、この **1 段目を最初から済ませておくための書き方**。単独ならどちらの変換も許されるのに、連続すると許されない、というのが分かりにくい点。

- `long x = 1;` … ○(拡大変換だけ)
- `Long x = 1L;` … ○(ボックス化だけ)
- `Long x = 1;` … ✗(拡大変換 + ボックス化の 2 段)

## なぜ id は Long なのか — DB のカラム型から決まっている

Java 側の都合で選んでいるのではなく、**テーブル定義から逆算されている**。

```sql
-- V1__create_base_tables.sql
CREATE TABLE categories (
    id            BIGINT      NOT NULL AUTO_INCREMENT,
    name          VARCHAR(30) NOT NULL,
    display_order INT         NOT NULL,
```

| MySQL | サイズ | Java |
|---|---|---|
| `INT` | 4 バイト | `int` / `Integer` |
| **`BIGINT`** | **8 バイト** | **`long` / `Long`** |

`id` が `BIGINT` なのは、レコードが 21 億件を超えても破綻しないようにするため(`INT` だと約 21 億で頭打ち)。id に `BIGINT` を使うのは Web アプリの定石。

同じテーブルの `display_order` は `INT` なので、Java 側も `Integer` になっている。**カラム型と Java のフィールド型がきちんと 1 対 1 で対応している**。

```java
// Category.java
private Long id;              // ← BIGINT に対応
private Integer displayOrder; // ← INT に対応
```

`CategoryResponse` の `id` が `Long` なのも元をたどればこの `BIGINT` に行き着く。だからテストで値を作るときも `1L` と書く必要がある。

## 同じ id の旅路 — MySQL → Java → JSON → TypeScript

このリポジトリでは、1 つの id が層をまたぐたびに姿を変えている。

```
① MySQL          id = 1           BIGINT カラムの中の 1
      ↓ JPA が読み出す
② Java(Entity)   Long id = 1L     8 バイトの箱に入った 1
      ↓ CategoryResponse.from() で詰め替え
③ Java(DTO)      Long id = 1L     同じく 8 バイトの箱の 1
      ↓ Jackson が JSON に変換
④ JSON           "id": 1          型の区別が消えて、ただの数値 1
      ↓ フロントが受け取る
⑤ TypeScript     id: number       number 型の 1(frontend/app/types/category.ts)
```

**JSON には `long` も `int` も区別がない。** だから `CategoryControllerTest` の検証側は `.value(1)` と `L` なしで書ける。「Java の中でだけ型がうるさい」と切り分けて理解すると混乱しない。

## 小数にもサフィックスがある — f と d

`L` が `long` の頭文字だったのと同じで、`f` と `d` も**型名の頭文字**。

| サフィックス | 型 | サイズ | 読み |
|---|---|---|---|
| `L` | `long` | 8 バイト | 整数(大きいほう) |
| `f` | **`float`** | 4 バイト | 小数(単精度) |
| `d` | **`double`** | 8 バイト | 小数(倍精度) |

```
float  bytes = 4, max = 3.4028235E38
double bytes = 8, max = 1.7976931348623157E308
```

`float` は「浮動小数点数(floating-point number)」、`double` は「倍精度(double precision)」の略。`double` は `float` の倍のサイズを使うぶん、細かい値まで表せる。

### 整数と小数で「既定の型」が逆

ここが混乱しやすい。**Java は整数を書いたら `int`、小数を書いたら `double`** と解釈する。

| 書いたもの | Java の解釈 | 既定はどちら側か |
|---|---|---|
| `1` | `int`(4 バイト) | **小さいほう**が既定 |
| `3.14` | `double`(8 バイト) | **大きいほう**が既定 |

整数は小さい `int` が既定なので、`long` にしたいときに `L` を足す。小数は大きい `double` が既定なので、`float` にしたいときに `f` を足す。**足す方向が逆**になっている。

```java
float f = 3.14;   // ✗ エラー
float f = 3.14f;  // ○
```

```
error: incompatible types: possible lossy conversion from double to float
```

`Long x = 1;` のときとはエラーの理由が違う。あちらは「2 段の変換だから」だったが、こちらは **大きい箱から小さい箱に移そうとしている**(縮小変換)ため。8 バイトの値を 4 バイトに押し込めば桁が落ちるので、Java が止める。

### d はいつ使うのか — 整数同士の割り算を避けるため

小数の既定がすでに `double` なので、`3.14d` と書く機会はほぼない。`d` が効くのは**整数の割り算**の場面。

```
1 / 2    = 0       ← int ÷ int なので小数点以下が切り捨てられる
1d / 2   = 0.5     ← 片方を double にすると小数として計算される
```

`1 / 2` が `0` になるのは最も踏みやすい罠のひとつ。`1d` でも `1.0` でも `(double) 1` でもよいが、いずれも「これは小数の計算だ」と Java に伝えるための書き方。

## 小数の誤差とお金 — なぜ float / double を使ってはいけないか

`float` と `double` には、**サイズとは別の根本的な問題**がある。

```
0.1 + 0.2 == 0.3 -> false
```

### 原因 — 2 進数では 0.1 を書き表せない

`float` / `double` は数を **2 進数の小数**として保持する。ところが 2 進数で `0.1` を正確に表すことはできない。10 進数で 1÷3 が 0.3333... と終わらないのと同じことが、2 進数の 0.1 で起きる。

Java では `double` の中身を厳密な 10 進数として取り出せるので、正体が見える。

```java
new BigDecimal(0.1)
```

```
0.1000000000000000055511151231257827021181583404541015625
```

**`0.1` と書いたつもりの値は、実際には 0.1 ではない。** ごくわずかに大きい。

そして誤差の原因はこれだけではない。**double が表せる数はとびとび**で、数直線上の目盛りに乗る値しか保持できない。そのため **足し算の結果は毎回「一番近い目盛り」に丸め直される**。しかもこの目盛りの間隔は**数が大きくなるほど粗くなる**。

```
ulp(0.1) = 1.3877787807814457E-17   ← 0.1 付近の目盛りの間隔
ulp(7.0) = 8.881784197001252E-16    ← 7 付近の目盛りの間隔(64 倍粗い)
```

(`ulp` = Unit in the Last Place。その値の付近で表現できる隣の数までの距離)

結果として、足し込むほど 1 回あたりの丸め幅が広がっていく。

```
0.1 を 70 回足す = 6.999999999999991    ← 7.0 にならない
```

なお前述の `0.1f + 0.2f` が `0.3` と表示されたのは誤差が無いからではなく、**`float` は表示桁数が少ないので誤差が見えていないだけ**。むしろ精度が低いぶん状況は悪い。

### なぜ「大きすぎる値」を 70 回足したのに 7 未満になるのか

`0.1` の実体は 0.1 より**大きい**のだから、70 回足せば 7 を超えるはず — と考えるのが自然。実際、**誤差なく足せた場合の値は確かに 7 を超える**。

```
double(0.1) の厳密値    = 0.1000000000000000055511151231257827021181583404541015625
それを 70 倍した厳密値  = 7.0000000000000003885780586188047891482710838317871093750  ← 7 より大きい
実際に += を 70 回した値 = 6.9999999999999911182158029987476766109466552734375        ← 7 より小さい
```

ずれは **−9.27 × 10⁻¹⁵**。上振れするはずが下振れしている。原因は、**誤差の発生源が 2 つあり、大きいほうが小さいほうを完全に飲み込む**ため。

| | 誤差の発生源 | 1 回あたりの大きさ |
|---|---|---|
| ① | `0.1` そのものが大きすぎる分 | **5.55 × 10⁻¹⁸** |
| ② | 足すたびに目盛りへ丸め直される分 | 最大 **8.88 × 10⁻¹⁶**(7 付近) |

**②は①の約 160 倍。** さらに決定的なのが次の比較。

```
①の合計(5.55e-18 × 70 個)  = 3.89e-16
7 付近の目盛りの間隔        = 8.88e-16
```

**70 個分の超過を全部足しても、7 付近の目盛り 1 つ分の半分にも届かない。** つまり「0.1 が少しずつ大きい」という効果は、7 の近くでは**そもそも表現できる大きさではない**。目盛りが 1mm の物差しで 0.4mm の差を記録しようとしているようなもので、記録した瞬間に消える。残るのは②だけで、今回は下方向への丸めが積み重なり、最終的に**約 10 目盛り分下**にずれた。

### 誤差の向きは一定ではない

途中経過を「誤差なく足せた場合の値」と比べると、ずれが増えたり減ったりしているのが分かる。

| 回数 | 理想値とのずれ | |
|---|---|---|
| 1 回目 | **0** | ぴったり |
| 2 回目 | **0** | ぴったり |
| 3 回目 | **+2.78 × 10⁻¹⁷** | 上振れ |
| 4 回目 | **0** | たまたま戻った |
| 8 回目 | −1.11 × 10⁻¹⁶ | 下振れが始まる |
| 10 回目 | −1.67 × 10⁻¹⁶ | |
| 70 回目 | −9.27 × 10⁻¹⁵ | |

1 回目と 2 回目が誤差ゼロなのは、**2 倍は指数部を 1 増やすだけで正確に表せる**ため。3 回目で初めて目盛りに乗らない値が出て上振れし、4 回目で偶然元に戻り、8 回目以降は下振れが続いている。

**誤差は「一方向にきれいに積もる」ものではなく、増減しながら漂う。** だから「何回足したらどれだけずれるか」を頭で予測することはできず、`==` での比較が当てにならない。金額計算に使ってはいけない理由はここにある。

### 対策 1 — BigDecimal を使う

`BigDecimal` は数を **10 進数のまま**保持するクラス。2 進数に変換しないので、この種の誤差が出ない。

```
"0.1" + "0.2" = 0.3     ← BigDecimal での加算
```

ただし `BigDecimal` 自体に 3 つの罠がある。

**罠 1: `double` から作ってはいけない。** 引数に `double` を渡すと、すでに誤差を含んだ値がそのまま取り込まれる。

```
new BigDecimal(0.1)   = 0.1000000000000000055511151231257827021181583404541015625  ← ✗ 誤差ごと入る
new BigDecimal("0.1") = 0.1                                                         ← ○ 文字列で渡す
```

**罠 2: `equals` は桁数まで比較する。** 値が等しいかを見たいときは `compareTo` を使う。

```
new BigDecimal("1.0").equals(new BigDecimal("1.00"))    = false   ← 桁数が違うと別物扱い
new BigDecimal("1.0").compareTo(new BigDecimal("1.00")) = 0       ← 値としては等しい
```

**罠 3: 割り切れない割り算は例外になる。** 丸め方を指定しないと落ちる。

```
new BigDecimal("1").divide(new BigDecimal("3"))
  -> ArithmeticException: Non-terminating decimal expansion; no exact representable decimal result.

new BigDecimal("1").divide(new BigDecimal("3"), 2, RoundingMode.HALF_UP) = 0.33
```

「勝手に丸めず、どう丸めるかを必ず書かせる」という設計。お金の計算では切り捨て・四捨五入・切り上げのどれを使うかが業務ルールで決まっているので、**明示させるほうが安全**という思想になっている。

### 対策 2 — 整数で持つ

もう一つの定番が、**最小単位の整数で持ってしまう**方法。日本円なら「円」、ドルなら「セント」を単位にする。

```java
private Integer priceYen;   // 1200 = 1200 円
private Long priceCents;    // 1250 = $12.50
```

小数を一切使わないので誤差が原理的に発生せず、計算も速い。消費税のような割合計算が入る箇所だけ慎重に丸める。**扱う通貨と精度が固定なら、この方式のほうが単純で堅い。**

### DB 側との対応

整数のときに `BIGINT` → `Long` という対応があったのと同じく、小数にも対応関係がある。

| MySQL | Java | 用途 |
|---|---|---|
| `DECIMAL(p, s)` | **`BigDecimal`** | 金額など、誤差が許されない値 |
| `DOUBLE` / `FLOAT` | `Double` / `Float` | 座標・測定値など、多少の誤差を許せる値 |
| `INT` / `BIGINT` | `Integer` / `Long` | 「円」「セント」単位で持つ場合はこちら |

`DECIMAL` は MySQL 側でも 10 進数のまま保持する型。**金額カラムは `DECIMAL`、Java 側は `BigDecimal`** が定石の組み合わせになる。

> **このプロジェクトでの状況** — 投稿アプリなので金額を扱う場所が無く、マイグレーション・エンティティともに小数のカラムは 1 つも存在しない(`display_order` すら `INT`)。つまり `float` / `double` / `BigDecimal` の出番は今のところゼロ。将来ここに金額が入るときのための知識としてまとめてある。

## 他の言語ではどうか

「リテラルに型を指定する」「書いただけだと int」という発想は Java 固有のものではないが、**言語によって有無がはっきり分かれる**。分かれ目は「その言語が整数型を何種類持っているか」。

### PHP — 整数型は 1 種類。サフィックスは無い

PHP の整数型は **`int` の 1 種類だけ**。`long` も `short` も無いので、**書き分ける必要がなく、リテラルに型を指定する文法も存在しない**。

```php
$id = 1;        // int。これ以外の書き方は無い
echo PHP_INT_MAX;  // 64bit 環境なら 9223372036854775807(Java の long と同じ大きさ)
```

サイズは環境依存で、64bit 環境では 8 バイト。つまり **PHP の `int` は実質 Java の `long` 相当**であり、Java でいう `int`(4 バイト)にあたる型が無い。だから「どちらの箱にするか」という選択自体が発生しない。

注意すべきは範囲を超えたときの挙動で、**PHP は静かに `float` に化ける**。

```php
var_dump(PHP_INT_MAX + 1);  // float(9.2233720368548E+18) ← int ではなくなる
```

Java なら `long` を超えると桁あふれ(オーバーフロー)して負の値に回り込むが、PHP は型そのものが変わる。**どちらも気づきにくいが、方向性が違う**。

### TypeScript / JavaScript — number は 1 種類。ただし BigInt には `n` が付く

JavaScript の数値型は **`number` の 1 種類**で、整数専用の型が無い。実体は **IEEE 754 の倍精度浮動小数点**、つまり Java でいう `double` 相当のものが整数も担当している。

```ts
const id: number = 1   // 整数も小数も同じ number
```

小数で整数を表しているため、**正確に扱える整数には上限がある**。

```
Number.MAX_SAFE_INTEGER = 9007199254740991   (2^53 - 1、約 900 兆)
9007199254740993 => 9007199254740992         ← 超えると静かに丸められる
```

エラーにならず**値が変わる**のが厄介な点。

そして 2020 年に **BigInt** が追加され、ここで初めて **リテラルにサフィックスを付ける文法**が JavaScript に登場した。

```
typeof 1n = bigint | 1n == 1 -> true    ← 値としては 1 と等しい
1n + 1 => TypeError: Cannot mix BigInt and other types
```

**`1n` は Java の `1L` に一番近い存在**。「値は同じ 1 だが型が違う」「型をまたぐ自動変換をしてくれない」という性質までよく似ている。TypeScript でも `number` と `bigint` は別の型として扱われる。

ただし BigInt には JSON との相性問題がある。

```
JSON.stringify({id: 1n}) => TypeError: Do not know how to serialize a BigInt
```

### 3 言語の比較

| | 整数型の種類 | リテラルの型指定 | 既定の型 | 範囲を超えたら |
|---|---|---|---|---|
| **Java** | 4 種類(byte/short/int/long) | **あり**(`1L`) | `int`(4 バイト) | オーバーフローして負に回り込む |
| **PHP** | 1 種類(int) | **なし**(不要) | `int`(64bit 環境で 8 バイト) | `float` に化ける |
| **TypeScript / JS** | 1 種類(number)+ BigInt | **BigInt のみあり**(`1n`) | `number`(倍精度小数) | 2^53 超で静かに丸められる |

**「型指定の文法があるかどうか」は、その言語が同じ「整数」に対して複数の入れ物を用意しているかどうかで決まる。** 入れ物が 1 つしかない言語には、指定する必要も文法も無い。

## このリポジトリでの落とし穴 — BIGINT を number で受けている

上の「旅路」を見ると、`BIGINT`(8 バイト整数)を最終的に TypeScript の `number`(2^53 まで)で受けていることが分かる。

```ts
// frontend/app/types/category.ts
export interface Category {
  id: number      // ← Java 側は Long、MySQL 側は BIGINT
  name: string
}
```

JSON をパースした時点で丸めが起きるため、フロント側で防ぐ手立ては無い。

```
JSON.parse('{"id":9007199254740993}').id => 9007199254740992
```

**いつ壊れるか** — id が `9,007,199,254,740,991`(約 900 兆)を超えたとき。

**現状の評価 — 問題なし。** id は `AUTO_INCREMENT` で 1 ずつ増える学習用アプリなので、この桁に到達することはない。対応は不要。

### 危ないのは件数ではなく「id の作り方」

「900 兆件も入らないから安心」と言えるのは、**id が `AUTO_INCREMENT` で 1 ずつ増える場合だけ**。時刻から id を組み立てる採番方式では、話がまったく変わる。

代表例が Twitter の作った **Snowflake ID**。ビットの内訳はこうなっている。

```
[ 41 bit: タイムスタンプ(ミリ秒) ][ 10 bit: マシン番号 ][ 12 bit: 連番 ]
 ←──────────── 22 ビット左にずらされる ────────────→
```

**タイムスタンプが 22 ビット分(= 約 419 万倍)左にずらされる**のがポイント。元々大きい「時刻」をさらに 419 万倍した値が id になるので、**1 件目のレコードからいきなり 19 桁になる**。

| 採番方式 | 2^53 に到達する条件 |
|---|---|
| `AUTO_INCREMENT` | **約 900 兆件**のレコードが必要 → 事実上到達しない |
| Snowflake(独自の起点) | `2^53 ÷ 2^22 = 2^31` ミリ秒 = **約 25 日** |
| Snowflake(Unix 時刻起点) | **初日から超えている** |

Unix 時刻をそのまま使った場合の値を計算すると、桁違いなのが分かる。

```
Snowflake 風の id (2026年7月)  = 7,486,832,640,000,000,000
2^53(JS が安全に扱える上限)    =         9,007,199,254,740,992   ← 約 800 倍オーバー
```

「レコードが増えたら危ない」ではなく「**最初から壊れている**」というのが、この方式の怖いところ。Twitter はまさにこれに遭遇し、API のレスポンスに数値の `id` とは別に**文字列版の `id_str` を追加**した。

なお、この巨大な id は **`BIGINT` にも Java の `long` にも問題なく収まる**。

```
Snowflake 風の id = 7,486,832,640,000,000,000
long の最大値     = 9,223,372,036,854,775,807
```

**問題が起きるのは JavaScript に渡した瞬間だけ。** このメモ全体のテーマである「同じ数でも、層ごとに器の大きさが違う」が最も分かりやすく出る例。

> Snowflake のような方式を使う理由は、`AUTO_INCREMENT` の弱点を避けるため。DB が 1 台であることを前提にしない(複数サーバーが同時に採番できる)、連番でないので次の id を推測されない、登録件数が外部に漏れない、といった利点がある。

## つまずきポイント

- **`1L` と `1` は同じ値。** 別の数ではない。違うのは入れ物のサイズだけ
- **`L` を付けるかどうかは気分ではなく、受け取り側の型で機械的に決まる。** 引数が `Long` なら必須、`int` なら不要
- **単独の変換は OK でも、2 段続くと自動ではやってくれない。** `Long x = 1;` が通らない理由はこれ
- **小文字の `l` は使わない。** `1l` は数字の 1 と紛らわしい
- **整数と小数で既定の型が逆。** 整数は小さい `int`、小数は大きい `double` が既定。だから `L` は「大きくする」、`f` は「小さくする」ために付ける
- **`1 / 2` は `0` になる。** int 同士の割り算は小数点以下が切り捨てられる。`1d / 2` か `1.0 / 2` と書く
- **`new BigDecimal(0.1)` は誤差ごと取り込む。** `BigDecimal` には必ず文字列で渡す(`new BigDecimal("0.1")`)
- **`BigDecimal` の `equals` は桁数まで比較する。** `1.0` と `1.00` が別物になる。値の比較は `compareTo`
- **小数の誤差は「初期のズレが積もる」のではない。** 主因は足し算のたびの丸め直しで、その幅は数が大きくなるほど広がる。増減しながら漂うので、ずれの向きも大きさも予測できない
- **小数の `==` 比較は当てにならない。** `0.1 + 0.2 == 0.3` は `false`。比較が必要なら `BigDecimal` か整数にする
- **JSON になった時点で型の情報は消える。** テストで `.value(1)` と書けるのはそのため
- **PHP と JS は「静かに壊れる」方向。** Java は `L` の付け忘れをコンパイルエラーで教えてくれるが、PHP の float 化も JS の丸めも実行時に無言で起きる
- **BigInt は `JSON.stringify` できない。** BigInt を採用するなら API との境界で必ず変換が要る

## 用語集

- **リテラル** — ソースコードに直接書いた値そのもの。`1`、`"お知らせ"`、`true` など
- **サフィックス** — リテラルの末尾に付けて型を指定する記号。Java の `L`/`f`/`d`、JS の `n`
- **拡大変換(widening)** — 小さい箱から大きい箱への変換。`int` → `long` など。情報が失われないので自動で行われる
- **縮小変換(narrowing)** — 大きい箱から小さい箱への変換。`double` → `float` など。桁が落ちうるので自動では行われず、明示が必要
- **単精度 / 倍精度** — 小数を何ビット使って表すか。単精度が `float`(4 バイト)、倍精度が `double`(8 バイト)
- **BigDecimal** — 数を 10 進数のまま保持する Java のクラス。2 進数の誤差が出ないので金額計算に使う。生成は文字列から、比較は `compareTo`、割り算は丸め方の指定が必須
- **ボックス化(boxing)** — 基本型(`long`)をオブジェクト型(`Long`)に包む変換。`Long` は `null` になれるが `long` はなれない
- **基本型 / オブジェクト型** — `int`・`long` のように値そのものを持つ型と、`Integer`・`Long` のように値を包んだ箱。DB の未採番を `null` で表したいので、エンティティの id はオブジェクト型
- **オーバーフロー** — 型の表せる範囲を超えて値が回り込む現象。Java の `long` 上限を超えると負の値になる
- **IEEE 754 / 倍精度浮動小数点** — 小数を表す国際規格とその 64bit 版。JavaScript の `number` の正体
- **ulp(Unit in the Last Place)** — その値の付近で表現できる隣の数までの距離。double の「目盛りの間隔」で、値が大きくなるほど粗くなる。`Math.ulp(x)` で取れる
- **丸め直し** — 計算結果を表現可能な一番近い値にスナップすること。小数計算では毎回起きるため、誤差の主因になる
- **BigInt** — JavaScript で任意精度の整数を扱う型。リテラルは `1n`。`number` とは混ぜられない
- **AUTO_INCREMENT** — MySQL が id を 1 ずつ自動採番する仕組み
- **Snowflake ID** — 時刻・マシン番号・連番をビット連結して作る 64bit の id。DB に問い合わせず分散採番できるが、1 件目から巨大な値になる
