# ユーザー列挙を許容し、未確認アカウントへの再登録では既存の行を作り直す

日付: 2026-08-05
ステータス: accepted

## 決定

1. **「そのメールアドレスが登録済みか」を利用者に伝える。** 確認済みのメールアドレスで会員登録しようとしたら 400 + `fieldErrors.email` で「既に登録されています」と返し、未登録のメールアドレスでパスワードリセットを申請したら 400 で「登録されていません」と返す。つまり**ユーザー列挙(account enumeration)を意図的に許容する**
2. **未確認のメールアドレスで再度会員登録が来たら、既存の users 行を削除して最新の入力で作り直す。** 「確認メールをもう一度送るだけ」にはしない

## 背景と理由

### なぜ列挙を許容するのか

列挙対策の定石は「新規でも既存でも同じレスポンスを返し、既存の場合はメールで知らせる」だが、これを採ると**このリポジトリの目的である学習が阻害される**。

- 登録フォームで `fieldErrors` を使ったバリデーション表示を体験できない(既存メールでもエラーが返らないため)
- 開発中に「なぜエラーにならないのか」で毎回混乱する
- パスワードリセットで「登録されていないメール」を入力したときに何も起きないのは、学習中の動作確認では原因切り分けが困難

このアプリは**常時公開しない学習用アプリ**(CLAUDE.md)であり、列挙されて困る利用者が存在しない。実運用サービスなら逆の判断になるべきなので、**この決定は前提が変われば覆すもの**として記録する。

### なぜ未確認アカウントを作り直すのか

「確認メールをもう一度送るだけ」にすると穴が 2 つ残る。

**① 打ち間違いから復帰できない経路ができる**

登録リクエストには新しい username / 表示名 / パスワードが乗っているが、「送るだけ」だとそれらが捨てられる。最初の登録でパスワードを打ち間違えた人は、メールを確認した後もログインできない。しかもこの人は**パスワードリセットも使えない**(リセットは確認済みアカウント向けなので)。再登録しても DB のハッシュは古いままで、詰む。

**② pre-hijacking(事前登録によるアカウント乗っ取り)**

1. 攻撃者が `victim@example.com` + 攻撃者が知っているパスワードで登録する。確認メールは victim に届く
2. victim は「知らないメールだ」と無視する(この時点では未確認なので何も起きない)
3. 後日、victim が自分でこのアプリに登録しようとする
4. 「送るだけ」方式だと確認メールがもう一度届く。victim は自分の登録だと思ってリンクをクリックし、**アカウントが有効化される**
5. 有効化されたアカウントのパスワードは攻撃者のもの。victim は自分の入力したパスワードでログインできず首をかしげるだけだが、**攻撃者はログインできる**。しかも victim のメールアドレスに紐づいたアカウントなので、フェーズ4 の Google アカウントリンクまで巻き込む

これは 2022 年の研究で類型化された既知の攻撃(Microsoft や Dropbox でも報告例がある)で、対策の定石が「未確認アカウントに新しい登録が来たら、必ず最新の登録情報で置き換える」— つまり**攻撃者が仕込んだ資格情報を破棄すること**。

したがって「作り直す」の本質は古い資格情報を捨てることであり、手段としては `UPDATE` で上書きしても等価である。行の削除を選んだのは、`auth_tokens` が `ON DELETE CASCADE` なので**古い未使用トークンが自動で消える**という付随的な理由だけ。

削除して安全な根拠は、**未確認ユーザーはログインできないので投稿もいいねも持ち得ない**という不変条件。他のテーブルから参照されている行を消すことにはならない。

## 結果として生じること

- **「なぜ既存ユーザーを削除しているのか」は直感に反するので、コードにコメントを残す。** これを「危険な実装」と見て「送るだけ」に直すと、上記の脆弱性が入る
- **未確認の作り直しでも username の一意性は検証する。** 別人が既に使っている username で再登録してきたら、作り直す前に 400 + `fieldErrors.username` で弾く
- **未確認ユーザーがパスワードリセットを申請したら 400 で断り、確認メールの再送に誘導する。** リセットを未確認アカウントに許すと、メール確認を経ずにログインできる抜け道になる
- **確認メールの再送エンドポイントが必須になる。** 「メールが届かない」「期限が切れた」からの復帰経路がこれしかない
- **実運用サービスに転用するなら列挙対策を入れ直す必要がある。** 具体的には ① 登録・リセットのレスポンスを成否で分けない ② 差分は利用者本人にメールで伝える、の 2 点
