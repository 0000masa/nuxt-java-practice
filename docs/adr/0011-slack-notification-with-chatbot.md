# アラートの通知先をメールから Slack に移し、配線は Chatbot に任せる

日付: 2026-08-28
ステータス: accepted

## 決定

[ADR-0010](./0010-monitoring-in-ephemeral-stack.md) で作った検知層の通知先を、**SNS のメール購読から Slack に置き換える。** 配線は **Amazon Q Developer in chat applications(旧 AWS Chatbot)** に任せ、**Incoming Webhook も Lambda も使わない。**

- SNS トピック 2 本(`ecs-task-shortage` / `rds-alerts`)は**そのまま残す**。分割の軸も変えない
- `AWS::SNS::Subscription`(`Protocol: email`)2 本と `AlertEmail` パラメータを**削除する**
- `AWS::Chatbot::SlackChannelConfiguration` 2 本を**スタック内に**置き、トピック 1 本を Slack チャンネル 1 つに対応させる
- チャンネルは `#njp-alerts-ecs` / `#njp-alerts-rds` の 2 つ。**stg と prod で共用する**
- ワークスペース ID とチャンネル ID は**秘密ではないので `params/<env>.json` に平文で置く**

**アプリのエラーログ通知(ADR-0010 の E)は引き続き移植しない。** 判断は変わらない(理由は後述)。

手順 → [docs/slack/README.md](../slack/README.md)、設計 → [フェーズ15 の設計書](../superpowers/specs/2026-08-28-phase15-slack-notification-design.md)

## 背景と理由

ADR-0010 は、作り捨ての環境に常時稼働前提の検知層を持ち込んだ帰結を 4 つ受け入れた。**そのうち 1 つ目が実運用に入る前から明らかに重い。**

> **建てるたびに SNS の購読確認メールを 2 通踏む。** 踏むまでアラートは 1 通も届かない。スタックは緑、アラームも全部ある、なのに誰にも届かないという壊れ方をする。確認リンクは 3 日で失効し、SNS に再送 API は無い。トピックが 2 本なので、片方だけ踏み忘れるとその系統だけ無音になる。

これは**環境を建てるたびに必ず発生する手作業**で、しかも**失敗しても何も起きない**種類のものだった。「使いたいときだけ建てる」運用と最も相性が悪い。

Slack のチャンネルへの転送には購読確認の概念が無い。**通知先を移すだけで、この帰結が丸ごと消える。**

## なぜ webhook ではなく Chatbot か

**SNS の HTTPS 購読で Slack の Incoming Webhook URL を直接叩く構成は成立しない。** SNS は購読作成時に `SubscriptionConfirmation` を POST して `SubscribeURL` を踏ませるが、Slack の webhook は確認応答を返さないので購読が永久に `PendingConfirmation` になる。仮に確認できても、SNS の JSON エンベロープは Slack が期待するペイロード形式ではないので弾かれる。

つまり webhook を使うなら **SNS と Slack の間に整形役を挟むことが必須**で、選択肢は「自分でコードを書く」か「AWS に書いてもらう」かのどちらかしかない。**後者を選んだ。**

決め手は**アプリケーション以外のコードを持ちたくない**という判断。Lambda はアプリでもインフラ定義でもない第三のコードで、たとえ数十行でも、書けば所有物になり、ランタイムのバージョンも面倒を見ることになる。Chatbot はチャンネル設定を 2 つ書くだけで済み、アラーム本文の整形は AWS 側が持つ。

**副次的に、ADR-0010 の記述を 1 つ訂正する。** ADR-0010 は E(アプリのエラーログ通知)を落とした理由の一つとして「CloudFormation で Lambda を持つとコード zip の置き場が常駐 S3 として増える」と書いたが、**これは事実として誤り。** `AWS::Lambda::Function` の `Code.ZipFile` は Python / Node.js を 4096 文字以内でインラインに書けるので S3 は要らない。**それでも E を移植しない結論は変わらない**(後述)。

## 結果として生じること

### 1. Slack 側に、CloudFormation では作れない前提が 2 つできる

- **ワークスペースの認可**(AWS コンソールでの OAuth)。**1 回きりで、スタックを作り直しても消えない。**ホストゾーンや ECR と同じ常駐の手動設定が 1 つ増えた
- **各チャンネルへの `/invite @Amazon Q`**。これも 1 回きり

どちらも**欠けるとスタックは成功するのに通知だけ届かない。** ADR-0010 の帰結 1 と同じ「緑なのに機能していない」形が、**毎回から最初の 1 回に減った**という位置づけになる。

### 2. チャンネル設定は毎回作り直すことになる

Chatbot のチャンネル設定は、**対象の SNS トピックに自分自身を購読させる形で動く。** トピック名は `${ProjectName}-${EnvName}-...` 固定なので撤収後も ARN は変わらないが、**撤収でトピックが消えると購読も失われる。**設定を常駐の手動リソースにすると、次に建てたとき Chatbot 側から繋ぎ直すまで無音になる。

したがって設定はスタック内に置く。**Chatbot 用の IAM ロールも同様。**

### 3. Slack の無料プランでは履歴が 90 日で消える

有料プランを使う予定は無いので、**Slack は「直近 90 日の通知窓」であって記録の置き場ではない**という前提で運用する。CloudWatch 側にアラーム履歴は残るので実害は小さい。

### 4. ワークスペース ID とチャンネル ID が Git 履歴に残る

`AlertEmail` は `NoEcho` の必須パラメータにして GitHub の Environment secret から渡していたが、**Slack の 2 種類の ID は秘密ではない。** ID を知っていても、ワークスペースを認可済みの AWS アカウントからしか使えない(「知っていれば誰でも投稿できる」webhook URL とはここが違う)。`HostedZoneId` と同じ扱いで `params` に平文で置く。

**結果として `cfn-apply.yml` が短くなった。** `ALERT_EMAIL` の空文字ガードと `--parameters` への積み込みが消え、Environment secret も 5 つから 4 つに減った。**新しい仕組みを増やすどころか 1 つ減っている。**

### 5. E(アプリのエラーログ通知)は依然として実現しない

**CloudWatch Logs のサブスクリプションフィルタは SNS に送れない。** 送信先に指定できるのは Kinesis Data Streams / Firehose / Lambda / OpenSearch の 4 つだけで、Chatbot は SNS からしか受け取らない。**この 2 つは直接繋がらない。**

Chatbot には「カスタム通知」(所定の JSON を SNS に publish するとカード表示される)という口があるが、**その JSON を組み立てて publish する主体が要る**ので結局 Lambda になる。

したがって **ADR-0010 の「E は移植しない」という結論は、配線方式を変えても変わらない。** アプリ例外の通知が欲しくなったら Sentry を別途検討する。こちらは Spring Boot に SDK を入れる形なので**アプリケーションのコードとして扱える**という点で、Lambda とは性質が違う。

## 検討したが採らなかった選択肢

- **SNS → Lambda(`Code.ZipFile` のインライン Python)→ Incoming Webhook** — SNS トピック 2 本の構造をそのまま残せるうえ、webhook URL は `BasicAuthCredential` と同じ経路で渡せる。ADR-0010 が Lambda を避けた理由(zip 置き場の常駐 S3)はインライン記述で消えるので、技術的な障害は無かった。採らなかったのは**アプリケーション以外のコードを持ちたくない**という一点

- **EventBridge ルール → API Destination → Incoming Webhook** — Lambda もコードも無しで webhook を使える。CloudWatch アラームの状態遷移イベントと RDS イベントは EventBridge に流れるので配線自体は組める。採らなかったのは、**SNS トピック 2 本が消えて Terraform との 1 対 1 対応が崩れる**ことと、整形が `InputTransformer` の文字列組み立てに制限されること

- **メールと Slack の併用** — Slack 側の障害や設定ミスに気付けるが、**購読確認を毎回 2 通踏む手間がそのまま残る。**今回わざわざ移す理由の半分を捨てることになるので採らない

- **チャンネルを緊急度で 3 つに分ける** — ADR-0010 自身が「実務で通知先を分ける軸は『リソース種別』ではなく『緊急度』」と書いており、軸を選び直す機会ではあった。採らなかったのは、今回の変更が**宛先の付け替えであって検知層の設計軸の変更ではない**ため。トピックの再編は Terraform との対応も ADR-0010 の記述も同時に動かすことになる

- **stg と prod でチャンネルを分ける(4 チャンネル)** — 本番のアラートが検証のノイズに埋もれない。採らなかったのは、実際には stg しか建てないため半分が空のままになること、通知にアラーム名(環境名込み)が入るので判別できること。`params` でチャンネル ID を受ける形にしてあるので、**分けたくなったら値を差し替えるだけで済む**

- **`GuardrailPolicies` を `ReadOnlyAccess` にする** — 通知を見てその場で `describe` 系を叩ける。採らなかったのは、今回の用途が通知の一方向だけで必要な権限がゼロだから。**`AWSDenyAll` にして「通知専用である」ことをテンプレート上で明示する。**なお**このプロパティを省略すると `AdministratorAccess` が既定で適用される**ので、明示しないという選択肢は無い
