# 検証環境の Basic 認証は WAF のカスタムレスポンスで実装する

日付: 2026-08-19
ステータス: accepted

## 決定

AWS 上の検証環境(stg)を外部から隠すための Basic 認証は、**ALB に関連付けた WAF の Web ACL** で実装する。アプリのコードには一切入れない。

- `Authorization` ヘッダーが `Basic <base64>` と完全一致**しない**リクエストを Block する
- Block 時のカスタムレスポンスで **401 と `WWW-Authenticate: Basic realm="restricted"`** を返す
- 資格情報は `BasicAuthCredential`(`NoEcho` パラメータ)で受け、テンプレート内で **`Fn::Base64`** して埋め込む
- `EnableBasicAuth` パラメータと `Condition` で、Web ACL と関連付けを**まるごと作らない**選択ができる(stg=true / prod=false)
- **AWS マネージドルールは入れない**

## 背景と理由

`docs/infrastructure/README.md` の方針は「常時公開しない」だが、それは「使わないときは撤収する」という意味であり、**建てている間は URL を知っている人が誰でもアクセスできる**。ホスト名は ACM の証明書が証明書透明性ログ(CT)に載るので、発行直後から検索可能になる。会員登録・投稿・Google ログインを検証するので、隠す手段が要る。

参考にした Terraform リポジトリは、**CloudFront Functions** で同じことをしていた(`enable_basic_auth` 変数で stg/preview だけ有効)。しかしこのリポジトリは Nuxt を SSG ビルドして Spring Boot の `static/` から配信する構成(設計概要のアーキテクチャ決定 2)なので、**フロント配信用の CloudFront が存在しない**。ALB が直接リクエストを受けるため、同じ手は使えない。

### なぜ ALB のリスナールールでは不可能なのか

ALB のリスナールールは `http-header` 条件で `Authorization` の値を判定できる。しかし**不一致のときに返す `fixed-response` は、ステータスコード・本文・Content-Type しか指定できず、任意のレスポンスヘッダーを付けられない。**

Basic 認証は、サーバーが **401 と `WWW-Authenticate` ヘッダー**を返すことでブラウザに認証ダイアログを出させる仕組みである。このヘッダーが無いと、ブラウザは資格情報を尋ねる画面を出さない = 利用者は認証できない。ヘッダーなしの 401 を返すだけでは「アクセスできないページ」になってしまう。

**WAF のカスタムレスポンスは任意のヘッダーを付けられる**(`content-type` を除く)。ALB 構成で Basic 認証を成立させる手段としては、これが実質唯一である。

### なぜマネージドルールを入れないのか

Terraform 側の `waf.tf` は CloudFront に `AWSManagedRulesCommonRuleSet` 等を入れていた。ここでは入れない。

**フェーズ8 の検索ラボが SQL に似たキーワードを送る**設計になっているため、SQLi 検出のルールに引っかかって検証そのものが壊れる。参考にしたリポジトリに検索ラボは存在しないので、あちらの判断はそのまま持ち込めない。

## 検討したが採らなかった選択肢

- **セキュリティグループを CIDR で絞る** — 追加コストも追加リソースもゼロで、最も確実に隔離できる。採らなかったのは、外出先や別回線から確認できなくなり、そのたびにパラメータを直してスタックを更新することになるため。Terraform 側が Basic 認証を選んでいたのと同じ理由(IP に依存しない)
- **アプリに Basic 認証のフィルタを足す** — IP に依存せず、WAF の料金もかからない。採らなかったのは、フェーズ3・4 で組み上げた `SecurityConfig` に「本番では使わない仕組み」を混ぜることになり、認証の設定が読みにくくなるため。**インフラの都合はインフラ側で解く**という切り分けを優先した
- **ALB の組み込み OIDC 認証(`authenticate-oidc` アクション)** — AWS ネイティブで、Google を IdP にできる。しかし**アプリ自身が Google ログインを持っている**ため、ALB 側の Google 認証と二重になり、リダイレクトの経路が絡まる
- **何もしない** — CT ログの件があるので「知られていないから安全」は成立しない

## 結果として生じること

- **WAF の料金が発生する。** Web ACL が月 $5、ルールが月 $1(いずれも時間割り)+ リクエスト課金。数時間の検証なら数円だが、**撤収し忘れると月額が乗る**のは NAT Gateway・ALB・RDS と同じ
- **Basic 認証の資格情報は秘密の保護には使えない。** `SearchString` は WAF の設定値なので、`wafv2:GetWebACL` の権限がある者には読める。これは「公開を防ぐ薄い蓋」であり、認可の仕組みではない
- **ALB のヘルスチェックは WAF を通らない**(ALB 自身が生成するリクエストなので)。actuator の liveness が 401 になる心配はない
- **ブラウザ以外のアクセスにも資格情報が必要になる。** curl での動作確認は `-u user:pass` を付ける。Google ログインのコールバックはブラウザのナビゲーションなので、認証済みブラウザは資格情報を自動で再送する(要実測)
- `BasicAuthCredential` は `params/stg.json` には置かず、**GitHub の Environment secret からワークフローの `--parameter-overrides` で渡す**。パラメータファイルに秘密を置かないという線引きが `ImageTag` と同じ扱いで守られる
