# 認証メールを SQS 経由でワーカーサービスに送らせ、トークンの発行もワーカーで行う

日付: 2026-10-11
ステータス: accepted

## 決定

認証メール(メール確認・パスワードリセット)の送信を、Web のリクエスト処理から切り離す。
**Web はコミットの後に SQS へメッセージを送るだけにし、別の ECS サービス(ワーカー)が受け取って処理する。**
ワーカーは Web と同じイメージから `app.role=worker` で起動する。

メッセージは `requestId` / `userId` / `purpose` / `requestedAt` だけで、**生のトークンは載せない。**
**トークンの失効と発行、文面の組み立て、SES での送信はワーカーが行う。**

フェーズ3 の[設計の決定7](../superpowers/specs/2026-08-05-phase3-auth-design.md)
(コミット後にリクエストと同じスレッドで同期送信する)は、この ADR で置き換える。

## 背景と理由

会社では、2 つの ECS サービスの片方が SQS にメッセージを入れ、もう片方(送金処理)が取り出して処理している。
**その構成を手元で建てて理解すること**が目的。認証メールを選んだのは、すでに動いている機能で、
同期送信の弱点(レスポンスが SES を待つ / コミット直後に死ぬとメールが失われる)が改善前の基準として測ってあるため
(→ [application-events-vs-queues.md](../notes/java/spring/application-events-vs-queues.md))。

### なぜ世間の定番に反して、トークンをワーカーで発行するのか

Rails(Devise)や Laravel のパスワードリセットでは、**リクエストの中でトークンを発行し、生の値をジョブに載せてキューに入れる**のが定番。
フレームワークが「同期で送っていたメールを 1 行で非同期にする」作りになっているためで、発行する場所を変える発想がそもそも出てこない。

ここで逆を選んだ理由は 3 つ。

- **キューと DLQ に秘密が残らない。** DB にはハッシュしか保存していないのに、生のトークンが最長 14 日 DLQ に残るのは釣り合わない
- **会社の構成に近い。** 会社のワーカーは送金処理、つまりワーカー自身が DB を更新する業務処理を担う。
  「ワーカーが DB を書き換える処理が、重複配信で 2 回走ったらどうなるか」を同じ形で体験できる
- **同じイメージなので、ワーカーが DB に繋ぐ費用はほぼ払い済み。** Web と同じ設定で起動するだけで済む

### 引き換えに引き受けたもの

- **重複配信でトークンが 2 回発行されうる。** 1 通目のリンクが失効する。
  → Web が送る前に作る `requestId` を冪等キーにし、ワーカーが `processed_messages` に記録して止める。
  記録のコミットは SES での送信の**後**にする(失うよりは、まれに 2 通届くほうを選ぶ)
- **依頼の時点と発行の時点がずれる。** とくに「リセットを申請 → パスワードを変更 → ワーカーが発行」の順になると、
  パスワード変更による失効をすり抜けたリンクが届く。
  → `users.password_changed_at` を足し、`requestedAt` より後に変更されていれば送らない。
  **キューを入れたことで既存の保証を黙って弱めない**ことを優先した

## 検討したが採らなかった選択肢

- **Web で発行し、生のトークンをメッセージで運ぶ(定番)** — 変更は最小で済むが、上の理由で採らなかった。
  会社のキューに秘密が乗っていると分かっても、この判断は変えない(そのときは SSE-KMS を検討する)
- **完成したメール(宛先・件名・本文)を運び、ワーカーを汎用の送信役にする** — ワーカーが認証を知らずに済むが、秘密がキューに乗る点は定番と同じ
- **別プロジェクト・別イメージにする(会社の形)** — ECR・buildspec・パイプラインがほぼ倍になる。学びたいのはキューの振る舞いで、ビルドの仕組みではない
- **アウトボックス** — コミット直後の消失まで塞げるが、別の大きなテーマ。Web はコミットの後に SQS へ送り、その間の消失は再送で救う(今と同じ大きさの受容)

## 結果として生じること

- **会員登録などのレスポンスが SES を待たなくなる。** その代わり、メールが届くのはワーカーが処理した後になる
- **ECS のサービスが 2 つになる。** ワーカーは ALB を持たないので Blue/Green にできず、ローリング更新になる。パイプラインではワーカーを Web より先に更新する
- **ワーカーも Aurora の Writer に繋ぐ。** プールは 2 本に絞る(ADR-0016 の `max_connections` の枠)
- **SQS 用の SNS トピックと Slack チャンネルが増える**(DLQ と滞留のアラーム)。手作業が 1 つ増える
- **ローカルのコンテナが 2 つ増える**(ElasticMQ と `worker`)
- **凍結ブランチ `github-actions-deploy` には入らない**(ADR-0012)
