# Google ログインは同一メールのアカウントに自動でリンクする

日付: 2026-08-15
ステータス: accepted

## 決定

1. **Google ログインで届いたメールアドレスが既存ユーザーのものなら、本人への確認を挟まず `google_sub` を紐づける**(アカウントリンク)。以後、そのユーザーはパスワードでも Google でもログインできる
2. **ただし Google が `email_verified: false` を返したときは、リンクも新規作成もせずログインを拒否する**。`google_sub` が既に紐づいているユーザーのログインでは、このクレームを見ない
3. **メールアドレスが一致した既存ユーザーが未確認だった場合は、リンクせず行を削除して作り直す**(理由は [ADR-0003](./0003-account-enumeration-and-unverified-signup.md) と同じ)
4. **`google_sub` が一致したとき、`users.email` を Google 側の値で更新しない**

## 背景と理由

設計概要 §3 は「同じメールなら同一アカウントに統合する(統合型アカウント)」と決めている。決定1 はその実装方法の選択で、選択肢は 3 つあった。

| 案 | 内容 | 却下 / 採用の理由 |
|---|---|---|
| A | 自動でリンクする | **採用**。利用者から見て「同じメールアドレスなのに別アカウントができた」という事故が起きない |
| B | リンクせず別ユーザーを作る | `uk_users_email` があるので**そもそも作れない**。作れるようにするには「同じメールで複数ユーザー」を許すことになり、統合型アカウントという前提が崩れる |
| C | 「既存アカウントにリンクしますか?」と確認画面を挟む | 安全側だが、確認したところで**利用者は同じ主張(このメールは自分のもの)を繰り返すだけ**で、新しい情報が増えない。Google が所有権を確認済みである以上、追加の確認にはならない |

C を却下できるのは、**Google の `email_verified` が「この Google アカウントはこのメールアドレスの所有権を確認済み」を意味する**からである。この前提が崩れると A は成立しなくなる。それが決定2 の理由。

### なぜ `email_verified` を検査するのか

`email_verified` は通常の `@gmail.com` では常に true だが、Google Workspace の一部の構成では、ドメイン管理者が所有権を証明していないアドレスが false で返ることがある。これを見落とすと乗っ取りが成立する。

1. 攻撃者が `victim@example.com` を名乗る、所有権未確認の Google アカウントを用意する
2. Google ログインする。`email_verified` は false だが、アプリが見ていなければ通る
3. メールアドレスが一致するので、victim の**確認済みアカウント**にリンクされる
4. 攻撃者は victim としてログインできる

これは決定3(未確認の既存アカウントを作り直す)では防げない。あちらは**既存側が未確認**のケースを守るもので、こちらは既存側が確認済みでも通ってしまうため、別に塞ぐ必要がある。

**既にリンク済みのユーザーで `email_verified` を見ないのは**、`google_sub` が一致した時点で「過去に一度メールの所有権を確認した、同一の Google アカウント」であることが確定しているため。ここで拒否すると、Google 側の設定変更でログインできなくなる利用者が出る。

### なぜ `users.email` を更新しないのか

利用者が Google アカウントのメールアドレスを変更すると、`sub` は同じままメールだけが変わる。これを取り込みたくなるが、このアプリで `users.email` は**「メール確認を済ませた、パスワードリセットの送り先」**という独立した意味を持っている。

- 取り込むと、このアプリが一度も確認していないアドレスが「確認済み」の座に座る。パスワードリセットのメールがそこへ飛ぶ
- 新しいアドレスを別のユーザーが既に使っていれば、`uk_users_email` に当たってログイン自体が失敗する

Google は**ログインの手段**であって、メールアドレスの現在の持ち主の証明ではない、という切り分けを取る。

## 結果として生じること

- **Google 経由で作られたユーザーは `password_hash` が NULL になる。** パスワードログインはできず、パスワードを持ちたければパスワードリセットの経路で設定する(`docs/api/request-password-reset.md`)。この状態を画面に出すため `GET /api/auth/me` に `hasPassword` を足す
- **username をサーバーが自動生成する。** Google ログインには入力欄が無いため。メールのローカル部から作るので、**メールアドレスの前半が公開情報になる**(username は X の @xxx 相当)。フェーズ7 のプロフィール編集で変更できる前提で許容する
- **Google 側のメールアドレス変更に追随しない。** 利用者から見ると「Google のメールを変えたのに、このアプリのメールは古いまま」になる。プロフィール編集でメールアドレスを変える機能(フェーズ7 以降)を入れるなら、そちらで対応する
- **`email_verified` が false の利用者は Google ログインを一切使えない。** 通常の Gmail アカウントはこの分岐に入らないため実害は小さいが、拒否理由が分かるメッセージを返す必要がある
- **決定2 と決定3 は、どちらも「メールを鍵にして人物を特定する瞬間」を守るためのもの。** 片方だけでは穴が残るので、両方を同時に維持する必要がある
