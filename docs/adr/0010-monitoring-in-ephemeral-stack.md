# 作り捨ての環境に、常時稼働前提の検知層をそのまま持ち込む

日付: 2026-08-28
ステータス: accepted(**帰結 1 は [ADR-0011](./0011-slack-notification-with-chatbot.md) で解消。通知先はメールではなく Slack**)

## 決定

参考にした Terraform リポジトリの検知層(CloudWatch アラーム + SNS + ログの S3 アーカイブ)を、**構成を変えずに CloudFormation へ移植する。** 「使いたいときだけ建てて、終わったら全部消す」という運用と噛み合わない部分が出るが、**構成を歪めて解決せず、運用で吸収する。**

作るものは 5 つ。

| 群 | 内容 | 通知先 |
|---|---|---|
| A | RDS メトリクスアラーム 4 本(CPU / FreeStorage / FreeableMemory / DatabaseConnections) | `rds-alerts` |
| B | RDS ログのメトリクスフィルタ 2 本 + アラーム 2 本(`[ERROR]` / スロークエリ急増) | `rds-alerts` |
| C | RDS イベント購読(availability / failover / low storage ほか) | `rds-alerts` |
| D | ECS タスク数不足(Metric Math で `running < desired`) | `ecs-task-shortage` |
| F | 全ログ → Firehose → S3 アーカイブ | — |

**アプリのエラーログ通知(Terraform 側の Lambda 経由のメール)は移植しない。** 通知本文にログを入れられる形でないと管理しづらいため、Sentry などを別途検討する。

## 背景と理由

このリポジトリの stg は**数時間しか存在しない**。一方、検知層というものは常時稼働を前提に設計されている。両者を突き合わせると、構成を歪めれば消せる不整合がいくつも出てくる。

それでも歪めなかったのは、**このリポジトリの目的が「実務で通用する構成を書けるようになること」**だからである。運用の都合に合わせて検知層を削ると、残るのは「この環境でしか正しくない構成」になり、学習題材としての価値が落ちる。**運用の都合は運用の側で吸収し、構成は実務の形のまま置く。**

## 結果として生じること(受け入れた 4 つ)

> **後日の追記(2026-08-28)**: このうち **1 は解消した。** 通知先をメールから Slack(Amazon Q Developer in chat applications)に移し、SNS のメール購読そのものを無くしたため → [ADR-0011](./0011-slack-notification-with-chatbot.md)。**2・3・4 は残っている。**以下は当時の記録としてそのまま残す。

### 1. 建てるたびに SNS の購読確認メールを 2 通踏む(→ ADR-0011 で解消)

`AWS::SNS::Subscription` を `Protocol: email` で作ると、CloudFormation は購読を `PendingConfirmation` のまま作り、**確認を待たずに `CREATE_COMPLETE` になる。** リンクを踏むまでアラートは 1 通も届かない。**スタックは緑、アラームも全部ある、なのに誰にも届かない**という壊れ方をする。これは `AWS::SES::EmailIdentity` で既に踏んでいるのと同じ形。

- 確認リンクは **3 日で失効**し、SNS に再送 API は無い
- トピックが 2 本なので、**片方だけ踏み忘れるとその系統だけ無音になる**
- 対策は `cfn-deploy.yml` のジョブサマリに出す固定リマインダのみ。実際の未確認数を検査する案もあったが、Actions のロールに `sns:ListSubscriptionsByTopic` を足す必要があるので採らなかった

### 2. 建てるたびに「OK になりました」通知が 7 通届く

CloudWatch アラームのアクションは**状態遷移**で発火する。新規作成されたアラームは `INSUFFICIENT_DATA` から始まり、正常と判定されると `OK` に遷移するので、**異常が一度も起きていなくても `OKActions` が動く。** アラーム 7 本ぶん届く。

`OKActions` は Terraform どおり全アラームに付けている。ログ由来のアラーム(B)は「5 分間に N 件以上」という判定なので、イベントが止まれば必ず 5 分後に `OK` に戻り、**1 回の異常につき必ず 2 通**になる。これも受け入れる。

### 3. ログアーカイブは撤収のたびに全部消える

`LogArchiveBucket` をスタック内に置いたので、**アーカイブされたログは撤収で全消滅する。** ライフサイクルの「30 日で Glacier IR」「365 日で削除」は**一度も発火しない。**

つまり **F は保全機能としては動いていない。** 配線(サブスクリプションフィルタ → Firehose → S3)が正しいことを確認するための構成として置いている。バケットを手動管理の常駐リソースにすれば機能として成立したが、**常駐リソースを増やさないこと**と **Terraform と 1 対 1 の対応を保つこと**を優先した。

副作用として、**Firehose が 900 秒ごとに書きにくるバケットを撤収時に空にする**ことになり、「空にする → `delete-stack`」の間にフラッシュが挟まると `BucketNotEmpty` で `DELETE_FAILED` になる。`cfn-destroy.yml` に 1 回だけのリトライを入れて塞いだ。

### 4. スロークエリアラームはフェーズ8・10 の実験中に鳴り続ける

`long_query_time` は 1 秒、アラームは「5 分間に 5 件以上」。ところがフェーズ8(検索ラボ)とフェーズ10(index 実験)は、**100 万件の posts に index 無しのクエリを投げて遅さを観察する**のが目的なので、実験中はアラームが鳴り続ける。

閾値は緩めない。**通知量は人が判断して無視する。** このリポジトリを触るのは 1 人なので、通知が意味を持つ状況かどうかを常に知っているため。

**同じフェーズが検知の仕組みと衝突するのはこれで 2 回目。** 1 回目は WAF で、「マネージドルールは入れない。フェーズ8 の検索ラボが SQL に似たキーワードを送るので SQLi のルールに引っかかって検証が壊れる」(`app.yml`)という判断をしている。あちらは「入れない」で解決したが、スロークエリ検知はこの構成で唯一 DB の遅さを見る目なので外せない。

## 検討したが採らなかった選択肢

- **SNS トピックと購読を手動管理の常駐リソースにする** — 購読確認が最初の 1 回で済み、メールアドレスがテンプレートにもリポジトリにも現れず、「通知先はアプリより長生きする」という実務の実態にも合う。採らなかったのは、Terraform と 1 対 1 の対応を保つこと、および常駐リソース(ホストゾーン / ECR / OIDC / IAM ロール 4 / SSM 4 / テンプレート置き場)をこれ以上増やさないことを優先したため

- **ログアーカイブのバケットを常駐リソースにする** — **F が保全機能として本当に成立する唯一の形**だった。[ADR-0008](./0008-template-bucket-as-resident-resource.md) でテンプレート置き場を常駐にした先例もある。上と同じ理由で見送った

- **SNS トピックを 1 本に集約する** — 購読確認が 1 通で済み、「片方だけ無音」が起きなくなる。実務で通知先を分ける軸は「リソース種別」ではなく「緊急度」なので、ECS / RDS で分ける Terraform の形は理想的でもない。それでも 1 対 1 の対応を優先した

- **ALB のアラームを足す**(`TargetResponseTime` / `HTTPCode_ELB_5XX_Count`)— `TargetResponseTime` は「遅いが落ちてはいない」を捕まえる、この構成で唯一の目になるはずだった(B のスロークエリは DB 内の時間しか見ないので、速いクエリを 200 回投げる N+1 は素通りする)。Terraform に無いものを増やさない判断で見送った

- **アプリのエラーログ通知(E)をメトリクスフィルタ + アラームで作る** — Lambda を持ち込まずに済むが、**通知本文にログの中身が入らない。** Terraform 側が Lambda を挟んでいるのはそのためで、そこを落とすと管理しづらい。どちらも採らず Sentry などを別途検討する

  > **訂正(2026-08-28)**: ここには当初「CloudFormation で Lambda を持つとコード zip の置き場が常駐 S3 として増える」と書いていたが、**これは誤り。** `AWS::Lambda::Function` の `Code.ZipFile` は Python / Node.js を 4096 文字以内でインラインに書けるので S3 は要らない。**E を移植しないという結論は変わらない**(理由は「アプリケーション以外のコードを持ちたくない」であって、S3 が増えることではなかった)。なお **Chatbot に移しても E は実現しない** — CloudWatch Logs のサブスクリプションフィルタは SNS に送れないため → [ADR-0011](./0011-slack-notification-with-chatbot.md)

- **スロークエリの閾値をパラメータに開き、実験時に上げる** — `params` を書き換えて `cfn-apply` するので commit が要る。実験のたびには重い

- **`ContainerInsights` の `disabled` を残す** — 残さなかった。D は `ECS/ContainerInsights` の `RunningTaskCount` / `DesiredTaskCount` に依存していて、標準の `AWS/ECS` に代替が無い。`params` を 1 行変えるだけで**アラームが残ったまま二度と鳴らなくなる**経路を塞いだ。**これは Terraform 側には無かった穴で、CloudFormation 化のときに新しく開いたもの**(Terraform は `enhanced` の直書き)
