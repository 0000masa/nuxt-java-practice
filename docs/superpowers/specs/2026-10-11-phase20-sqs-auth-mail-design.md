# フェーズ20: 認証メールを SQS 経由でワーカーサービスに送らせる

日付: 2026-10-11
ステータス: 設計済み・実装未着手

方針 → [ADR-0017](../../adr/0017-auth-mail-via-sqs-worker.md)。
フェーズ3 の[設計の決定7](./2026-08-05-phase3-auth-design.md)(メールはコミット後に同じスレッドで同期送信する)を置き換える。
背景の整理 → [application-events-vs-queues.md](../../notes/java/spring/application-events-vs-queues.md)(依頼の預け先の 4 段階のうち、①から④へ移る)

## 1. 目的

会社で使われている **「2 つの ECS サービスの片方が SQS にメッセージを入れ、もう片方が取り出して処理する」構成**を、このリポジトリで建てて理解する。
会社ではキューの先が送金処理で、別プロジェクト・別イメージになっている。ここでは題材を**認証メール**にし、イメージは 1 つにする(決定2)。

「理解する」を具体的な達成条件にすると、次の 4 つになる。

1. **ローカルでワーカーだけを止め、メッセージがキューに溜まる → ワーカーを戻すと流れる、を目で追えること**
2. **「受け取っただけでは消えない。処理後に削除しないと、可視性タイムアウトが切れて再配信される」を、手で動かして観察していること**
3. **重複配信が起きたとき、このアプリで何が起き、どこで止めているか(冪等キー)を説明できること**
4. **stg で、ワーカーのサービス・キュー・DLQ・アラームを自分で建てて動かしていること**

性能改善が目的ではない。ただし副産物として、会員登録などのレスポンスが SES の往復を待たなくなる。

## 2. いま何が動いているか

| 要素 | 現状 |
| --- | --- |
| メールを送る場面 | 会員登録 / 確認メールの再送 / パスワードリセットの申請 の 3 つ(`AuthService`) |
| 送り方 | `AuthService` がトークンを発行して `AuthMailRequestedEvent(toEmail, purpose, rawToken)` を発行 → `AuthMailSender` が `AFTER_COMMIT` で**リクエストと同じスレッドで同期送信** |
| トークン | 32 バイトの乱数。DB(`auth_tokens`)には SHA-256 ハッシュだけを保存。`issue` は同じ用途の未使用トークンを失効させてから発行する |
| 送信の実体 | 開発は Mailpit(SMTP)、本番は SES の API(`SesMailSender`、`MailSenderConfig` で切り替え) |
| ECS | Web のサービス 1 つ(CodeDeploy の Blue/Green)+ マイグレーション用のタスク定義 |
| 受容しているリスク | レスポンスが SES を待つ / コミット直後にプロセスが死ぬとメールは失われる(再送で救う) |

## 3. 制約として確定した事実

**(要検証)** が付いたものは、実装時に一次情報か実機で裏を取る。

### 3-1. DB にはトークンのハッシュしか無いので、生の値を後から取り出せない

「既存のトークンでメールを送り直す」はできない。再送のたびに失効 → 新規発行になる(今の `issue` の挙動)。

### 3-2. 標準キューは「少なくとも 1 回」届ける

同じメッセージが 2 回処理されることがある。原因は SQS 側の重複のほか、**処理を終えて削除する前に可視性タイムアウトが切れる**こと。
FIFO キューの重複排除は**送信時**の重複しか消さないので、処理の重複は防げない。

### 3-3. AWS SDK は `SendMessage` を自動でリトライする

1 回目が届いていて応答だけ失われた場合、2 通目に**別の `MessageId`** が付く。`MessageId` は冪等キーにならない。

### 3-4. 外部への副作用を伴う処理は「ちょうど 1 回」にできない

メール送信は DB のトランザクションに入らない。「記録をコミット → 送信」なら**まれに失う**、「送信 → 記録をコミット」なら**まれに重複する**。どちらに倒すかを選ぶしかない。

### 3-5. 会員登録は、同じメールアドレスの未確認ユーザーを削除して作り直す

作り直すと `userId` が変わる(ADR-0003)。古い依頼のメッセージは「ユーザーがいない」で自然に捨てられる。

### 3-6. パスワード変更は、発行済みのリセットリンクを失効させる

`changePassword` が `invalidateUnused(PASSWORD_RESET)` を呼ぶ。トークンの発行をワーカーに移すと、
**「申請 → 変更 → ワーカーが発行」の順になったとき、失効をすり抜けたリンクが届く**。決定11 で塞ぐ。

### 3-7. ALB を持たないサービスは Blue/Green にできない

CodeDeploy の Blue/Green はロードバランサーが必須で、ECS ネイティブの Blue/Green もロードバランサーか Service Connect が要る。
そもそもワーカーには切り替えるべき「入ってくるトラフィック」が無い。ワーカーはローリング更新になる。

### 3-8. ECS は、ヘルスチェックが無くても「プロセスが死んだ」ことは分かる

必須コンテナのメインプロセスが終わればタスクが止まり、サービスが `desiredCount` を保つために入れ替える。
分からないのは「**プロセスは生きているが仕事をしていない**」状態(受信スレッドだけが死んだ、固まった)。
この状態では受信回数が増えないので、**DLQ にも移らない**。

### 3-9. ECS の標準デプロイのアクションは、サービスの今のタスク定義を元にイメージだけ差し替える(要検証)

そうだとすると、`deploy/taskdef-*.json` で環境変数を Git 管理している今の方式と噛み合わない。決定15 の実装方法に影響する。

### 3-10. Spring Cloud AWS の Spring Boot 4 対応は未確認

4.x 系(4.1.1 まで)は出ているが、Boot 4 対応を明記した記述は見つけられなかった。決定6 で使わない理由の 1 つ。

## 4. 決定

### 決定1 対象は認証メールの 3 場面すべて

会員登録 / 確認メールの再送 / パスワードリセットの申請。送り方を場面ごとに変えない。

- 既存の機能なので、他のフェーズを待たずに着手できる
- 今の 3.57 秒(SES を待つレスポンス)と「コミット直後に死ぬと失う」が、そのまま改善前の基準になる
- 画像加工(フェーズ6 待ち)、S3 の掃除、CSV エクスポート、シードの分割投入も候補だったが採らなかった。
  キューの深さによるスケーリングを試すなら、大量に流しても害の無い画像加工のほうが向いている(決定16)

### 決定2 ワーカーは Web と同じイメージから、`app.role` で役割を切り替えて起動する

- プロパティ `app.role`(`web` / `worker`、既定は `web`)。受信ループの Bean に `@ConditionalOnProperty(name = "app.role", havingValue = "worker")`
- ワーカーのタスク定義では `APP_ROLE=worker` と `SPRING_MAIN_WEB_APPLICATION_TYPE=none` を渡す
- 既存の `app.task`(`TaskRunner`)と同じ考え方。プロファイルは環境の違い(開発 / 本番)に使い、役割の切り替えには使わない
- **別プロジェクト・別イメージ(会社の形)は採らなかった。** ECR・buildspec・パイプラインがほぼ倍になり、学びたいキューの振る舞いとは関係が薄い
- **呼び分け**: **ワーカー** = ECS のサービス・役割、**受信スレッド** = その中で受信ループを回すスレッド
- **(要検証)** Web を立てないとき、Spring Session(Redis)・Spring Security・OAuth2 の自動設定が引っ込むか。Redis への接続が作られるなら、ワーカーでは除外する

### 決定3 トークンの発行はワーカーで行う

メッセージには秘密を載せず、ワーカーが「古いトークンの失効 → 発行 → 文面の組み立て → SES で送信」を行う。

| 処理 | 担当 |
| --- | --- |
| 入力のチェックとエラー応答(400)、ユーザーの作成・作り直し | Web(今のまま) |
| `requestId` を作って SQS に送る(コミットの後) | Web |
| 処理する時点での状態の再確認(決定11) | ワーカー |
| トークンの失効と発行(ハッシュ化して保存) | ワーカー |
| 処理済みの記録(決定8)、文面の組み立てと送信 | ワーカー |

- **世間の定番は逆**(Web で発行し、生のトークンをジョブに載せる。Rails の Devise や Laravel のパスワードリセット)。
  それでもこちらを選んだ理由は ADR-0017
- パスワード変更時の `invalidateUnused` は Web に残る

### 決定4 メッセージは `requestId` / `userId` / `purpose` / `requestedAt` の JSON

```json
{
  "requestId": "6f1c0d2e-....(UUID)",
  "userId": 123,
  "purpose": "PASSWORD_RESET",
  "requestedAt": "2026-10-11T12:34:56.789Z"
}
```

- **冪等キーは Web が送る前に作る `requestId`。** `MessageId` は SDK のリトライで変わる(3-3)
- **宛先はメールアドレスではなく `userId`。** 作り直されたユーザー宛てに古い依頼が処理されない(3-5)
- `requestedAt` は決定11 の比較に使う。SQS の `SentTimestamp` でも代わりになるが、本文に明示したほうがテストで値を作りやすい
- **バージョン番号は持たない。** 変更は項目の追加だけに限り、ワーカーは**知らない項目を無視する**(JSON の読み込みで未知のフィールドをエラーにしない)

### 決定5 Web はコミットの後に SQS へ送る

今の `@TransactionalEventListener(AFTER_COMMIT)` の中身を「SES で送る」から「SQS に送る」に置き換える。

- 送信に失敗した、またはその直前にプロセスが死んだ場合は**メッセージが無いまま**になる。再送ボタンで救う(今と同じ大きさの受容)
- **トランザクションの中で送るのは採らなかった。** ワーカーがコミット前のユーザーを読めない、ロールバック後もメッセージが残る
- **アウトボックスは採らなかった。** 学習メモの③にあたる別の大きなテーマで、1 フェーズ分の大きさになる。今回は④(外部キュー)を体験するのが目的

### 決定6 SQS は AWS SDK v2 の `SqsClient` を直接使い、受信ループを自分で書く

- 依存は `software.amazon.awssdk:sqs` を 1 行足すだけ(BOM `2.54.0` は導入済み)。SES と書き方が揃う
- 受信: `receiveMessage`(ロングポーリング 20 秒)→ 処理 → 成功なら `deleteMessage`、例外なら削除しない
- **Spring Cloud AWS(`@SqsListener`)は採らなかった。** 学びたい部分(削除の時機、可視性タイムアウト、再配信)が隠れる。Boot 4 対応も未確認(3-10)。
  一度こちらで仕組みを理解したあとに置き換えて差を見るのはあり

### 決定7 開発環境の SQS は ElasticMQ

- `softwaremill/elasticmq-native` を docker-compose に足す。キューと DLQ は設定ファイルで起動時に作る
- MinIO(S3)・Mailpit(SES)と同じ「1 サービスにつき専用の代わりを 1 つ」の方針に合う。LocalStack は採らなかった
- **ローカルで確かめられないもの**: IAM の権限、キューポリシー、暗号化。stg で確かめる
- 本物とは別の実装なので、フェーズ18 の `CONFIG` コマンドのような「ローカルでは通るのに AWS で落ちる」は起こりうる

### 決定8 重複配信は冪等キーで止め、「送ってからコミット」で失わない側に倒す

- 新しいテーブル `processed_messages`(`request_id` を主キー、処理日時)。マイグレーションは V5 以降
- ワーカーは 1 件につき次の順で処理する

  1. トランザクションを開始する
  2. `processed_messages` に `request_id` があれば、何もせずにトランザクションを終え、メッセージを削除する
  3. 状態を再確認し(決定11)、送る必要が無ければ `processed_messages` に記録してコミットし、削除する
  4. トークンを失効・発行し、`processed_messages` に記録する
  5. **SES で送る**
  6. **コミットする**
  7. メッセージを削除する

- 5 と 6 の間で死ぬと再配信で**もう 1 通届く**。その逆(記録をコミットしてから送る)は、送信失敗のときに**永久に送られない**(3-4)。メールが届かないより 2 通届くほうがましと判断した
- ワーカーはユーザーを待たせないので、トランザクションを SES の往復時間だけ開いたままにしてよい(Web 側で決定7 が避けた形を、ワーカーでは許容する)
- `auth_tokens` に `request_id` 列を足す案は採らなかった。冪等性はキューを使う側の都合で、認証のテーブルに混ぜない。今後キューを使う処理にも使い回せる
- **掃除の仕組みは作らない。** メインキューの保持期間(決定10)より古い行は二度と参照されないので消してよい、とだけ記録する

### 決定9 ワーカーの処理は読み書きトランザクション 1 つで行い、Writer に繋ぐ

`@Transactional(readOnly = true)` を付けない。Reader から読むと、コミット直後の新規ユーザーがレプリカ遅延で見えないことがある(ADR-0016)。

### 決定10 失敗は 3 種類に分け、リトライと DLQ は SQS の設定に任せる

| 種類 | 例 | 扱い |
| --- | --- | --- |
| 送る必要がなくなった | 確認済み、ユーザーがいない、申請後にパスワードが変更された | 正常終了として削除(ログを残す) |
| 一時的な失敗 | SES のスロットリング、DB の接続断 | 削除しない → 可視性タイムアウト後に再配信 |
| 何度やっても失敗する | 形式が壊れている、想定外の例外が続く | `maxReceiveCount` で DLQ に移る |

ワーカーのコードは「成功または送る必要なし → 削除」「例外 → 削除しない」の 2 通りだけ。リトライ回数を自前で数えない。

| 項目 | 初期値 | 理由 |
| --- | --- | --- |
| 可視性タイムアウト | 60 秒 | 1 件は DB と SES で数秒の想定。十分に余裕を取る |
| `maxReceiveCount` | 5 | |
| メインキューの保持期間 | 1 日 | メール確認のトークンは 24 時間、リセットは 1 時間で切れる。それより長く残しても送る意味がない |
| DLQ の保持期間 | 14 日 | 調べる時間を確保する。中身に秘密は無い |

### 決定11 ワーカーは処理する時点の状態を再確認する

| 場面 | 送る条件 |
| --- | --- |
| 会員登録 / 確認メールの再送 | ユーザーが存在し、まだ確認していない |
| パスワードリセットの申請 | ユーザーが存在し、確認済みで、**`requestedAt` より後にパスワードを変更していない** |

- **`users` に `password_changed_at` を足す**(マイグレーション)。パスワードの変更とリセットの完了で更新する
- `updated_at` は表示名の変更などでも更新されるので代わりにならない
- 受け入れる案(穴として明記するだけ)は採らなかった。**キューを入れたことで、既存の保証(変更すると発行済みのリセットリンクが失効する)を黙って弱めない**
- 再送を 2 回押して逆順に処理された場合は、最後に処理されたほうが有効になる。今でも 2 回押せば同じことが起きるので受け入れる

### 決定12 ワーカーは SIGTERM で行儀よく止まる

1. SIGTERM を受けたら新しい受信をやめる
2. 処理中のメッセージは最後まで終えて削除する
3. 終了する

- Spring Boot のグレースフルシャットダウンに乗せ、受信ループをシャットダウンのフックで止める
- `stopTimeout` は既定の 30 秒のまま。ロングポーリング(最大 20 秒)の途中なら、受信を待たずに抜けられる作りにする
- 強制終了されても、削除前のメッセージは再配信され、冪等キーで救われる。それでも止め方を作るのは、Spot の中断(決定17)とローリング更新のたびに起きるため

### 決定13 「生きているのに働いていない」は、プロセス終了・タイムアウト・滞留アラームで防ぐ

- **受信スレッドが想定外に終わったら、アプリごと終了する。** ECS が入れ替える(3-8)。Laravel の `queue:work` と同じ「直すより作り直してもらう」考え方
- **外部への通信(SQS・SES・DB)にはすべてタイムアウトを設定する。** 固まる代わりに例外にして、通常のエラー処理(削除しない → 再配信)に乗せる。
  SQS の受信はロングポーリングの 20 秒より長いタイムアウトにする
- **キューの滞留アラーム**で、それでも直らない場合に人が気づく(決定19)
- **ハートビート(ファイルの更新日時 + コンテナのヘルスチェック)は見送った。** 実務ではワーカーにコンテナのヘルスチェックを設定しないことも多く、固まる原因の大半はタイムアウトで防げる

### 決定14 キューは SSE-SQS + 最小権限 + HTTPS 以外の拒否で守る

メッセージに秘密は無いが、それでも守る。

- **保存時の暗号化は SSE-SQS**(DLQ も同じ)。SSE-KMS は、守る中身が無いので利点(鍵の利用記録、復号できる人の限定)が効かない。
  自分で作る KMS の鍵は削除に 7〜30 日の待ちがあり、作り捨てのスタックと噛み合わない
- **権限を役割で分ける**
  - Web のタスクロール: このキューへの `sqs:SendMessage` だけ
  - ワーカーのタスクロール: このキューへの `sqs:ReceiveMessage` / `sqs:DeleteMessage` / `sqs:ChangeMessageVisibility` だけ
- **キューポリシーで `aws:SecureTransport` が `false` の操作を Deny する**(メインキューと DLQ)
- 会社のキューに秘密が乗っていると分かったら、SSE-KMS を検討し直す

### 決定15 ワーカーは同じパイプラインで、Web より先にローリング更新する

- Deploy ステージに ECS の標準デプロイのアクションを足し、`runOrder` でワーカー → Web の順にする。承認は 1 回のまま
- **受け取る側を先に新しくする**のは、デプロイ中に「新しい形式のメッセージを古いワーカーが読む」状況を生みにくくするため(決定4 の互換性の方針と組み)
- ローリング更新の設定: `minimumHealthyPercent: 100` / `maximumPercent: 200`、デプロイサーキットブレーカー(自動ロールバックあり)
- ALB のヘルスチェックが無いので、検知できるのは起動直後に落ちる失敗だけ。「起動したが処理できない」は DLQ のアラームで気づく
- 別のパイプラインにする案は採らなかった。同じイメージなのに承認が 2 回になり、両者のバージョンがずれる
- **(要検証)** 3-9。標準デプロイのアクションが Git 管理のタスク定義を反映できない場合は、buildspec でタスク定義を登録してサービスを更新する形などを検討する

### 決定16 台数は stg・prod とも固定 1 台。スケーリングは入れない

- **CPU 基準のスケーリングはワーカーに合わない。** 処理のほとんどが SES と DB の待ちで、キューに溜まっていても CPU は低いままになりうる
- キューの溜まり具合で増減するなら、AWS が推奨する「1 台あたりの滞留件数(待っている件数 ÷ 動いているタスク数)でのターゲット追跡」が本命。
  ただし認証メールの量では働く場面を作れず、試そうとすると本物の SES からメールが大量に出る。画像加工のような処理で試すときに回す
- 1 台が落ちても、メッセージはキューに残るので**止まるのではなく遅れるだけ**
- **既存の 2 段階デプロイ(`DesiredCount` 0 → N)に乗せる。** ワーカーも DB の `app` ユーザーで接続するので、DB ユーザーの作成前に起動すると落ちる

### 決定17 Fargate Spot の比率をパラメータにし、初期値は Spot のみ

- `WorkerSpotWeight` などを Web と同じ形で足す。stg・prod とも初期値は Spot のみ
- 中断されても、削除前のメッセージは再配信される(決定8・12 が中断への備えを兼ねる)。中断の通知から 2 分あるので、30 秒の `stopTimeout` で処理中の 1 件を終えられる
- Spot の空きが無いときは、パラメータの変更だけで通常の Fargate に逃がせる

### 決定18 受信スレッドは 1 本。Hikari は Writer 用に 2 本だけ

- 1 タスクの中ではメッセージを 1 件ずつ順に処理する。並列にするならタスクを増やす
- Writer の `max_connections`(90、ADR-0016)の枠を食わないよう、プールは 2 本。Reader のプールは持たない
- 1 回の `receiveMessage` で受け取る件数は **1 件**。10 件まとめて受け取って順に処理すると、後ろのメッセージは待っている間も可視性タイムアウトが進むため

### 決定19 アラームは 3 本。SQS 用の SNS トピックと Slack チャンネルを新しく作る

| アラーム | 条件(初期値) | 通知先 |
| --- | --- | --- |
| DLQ にメッセージがある | DLQ の `ApproximateNumberOfMessagesVisible` ≥ 1 | 新規: SQS 用(`#njp-alerts-sqs`) |
| キューの滞留 | メインキューの `ApproximateAgeOfOldestMessage` ≥ 300 秒 | 新規: SQS 用 |
| ワーカーのタスク数不足 | ワーカーの `RunningTaskCount` < 希望数 | 既存: ECS 用 |

- 「部品ごとに SNS トピックと Slack チャンネルを 1 組」の今の方針に合わせる(フェーズ18 の Redis と同じ)
- **「DLQ に入った(処理に失敗した)」と「誰も処理していない」は別の異常**なので、2 本とも置く(3-8)
- 手作業が 1 つ増える: Slack にチャンネルを作り、その ID を `params/*.json` の `SlackChannelIdSqs` に書き写す

### 決定20 ローカルでは `worker` コンテナを別に立てる

- `backend` と同じ `./backend` と Gradle のキャッシュをマウントし、`APP_ROLE=worker` で `bootRun` する
- 本番と同じ 2 プロセスになり、**ワーカーだけを止めて**溜まる様子と流れる様子を観察できる
- `gradlew classes` を 1 回実行すると、両方の devtools が再起動する
- **(要検証)** 同じプロジェクトのディレクトリで Gradle が 2 つ動いたとき、`build/` や `.gradle/` のロックがぶつからないか。
  ぶつかったら `--project-cache-dir` などで逃がし、それでも駄目なら開発時だけ `backend` の中で受信スレッドも動かす

### 決定21 テストは処理本体と送信の時機を必ず書き、受信ループは結合テストを 1〜2 本

| 対象 | 中身 | SQS |
| --- | --- | --- |
| ワーカーの処理本体 | 送る / 確認済みなので送らない / ユーザーがいないので送らない / 申請後にパスワードが変更されたので送らない / 同じ `requestId` の 2 回目は送らない | 不要(受信ループから切り離したメソッドを直接呼ぶ) |
| Web の送信 | コミットの後に 1 件送られる / ロールバックしたら送られない | 不要(`SqsClient` を差し替える) |
| 受信ループ | 受け取る → 処理 → 削除 / 例外のときは削除しない | ElasticMQ のテスト専用キュー |

- テスト専用のキューは、MySQL と同じく**同じ ElasticMQ のコンテナでキュー名を分ける**(`auth-mail-test` など)
- 可視性タイムアウトによる再配信や DLQ への移動といった **SQS 自体の振る舞いはテストに書かず、手で動かして観察する**(§7)。待ち時間が長く、アプリではなく SQS の仕様のため

### 決定22 フェーズは 1 つにし、ADR はワーカーへの切り出しの 1 本だけ作る

ADR-0017 で、フェーズ3 の設計の決定7 を置き換えたことを明記する。

## 7. 実機で確かめること

### ローカル

- ワーカーを止めて登録 → メッセージが溜まる → ワーカーを起動すると流れて Mailpit に届く
- 処理の途中で例外を投げる → 削除されず、60 秒後に再配信される → 5 回で DLQ に移る
- 同じ `requestId` のメッセージを手で 2 回送る → メールは 1 通だけ
- 処理中に `docker compose stop worker` → 処理中の 1 件を終えてから止まる
- 会員登録のレスポンス時間が、SES(Mailpit)の往復を待たなくなる
- 要検証: Gradle 2 つの同居(決定20)、Web を立てないときの自動設定(決定2)

### AWS(stg)

- ワーカーのサービスが 2 段階デプロイで起動し、SES からメールが届く
- Web のタスクロールで受信できない / ワーカーのタスクロールで送信できない(権限の分離)
- HTTP(TLS なし)での操作が拒否される
- DLQ と滞留のアラームが `#njp-alerts-sqs` に届く
- パイプラインでワーカー → Web の順に更新される。ワーカーがローリング更新で 0 台にならない
- 要検証: 3-9(標準デプロイのアクションとタスク定義の関係)

## 8. やらなかったこと

| やらなかったこと | 理由 | やるとしたら |
| --- | --- | --- |
| アウトボックス | 別の大きなテーマ(決定5) | コミット直後の消失まで塞ぎたくなったとき |
| キューの深さによるスケーリング | 認証メールでは働く場面が作れない(決定16) | 画像加工などをキューに載せるとき |
| ハートビートとコンテナのヘルスチェック | 実務でも無いことが多く、タイムアウトで大半を防げる(決定13) | 受信スレッドが固まる事例が実際に出たとき |
| SSE-KMS | 守る中身が無く、作り捨てと噛み合わない(決定14) | 秘密を載せるメッセージを扱うとき |
| `processed_messages` の掃除 | 件数がごく少ない(決定8) | 行数が気になったとき。保持期間より古い行は消してよい |
| Spring Cloud AWS | 仕組みが隠れる、Boot 4 対応が未確認(決定6) | 自前のループで理解したあと、差を見るために置き換える |
