技術やコードの質問に**短く**答える。読者の目的は「読む負荷を抑えつつ、分からないところを理解してから次に進むこと」。
**調べる量は減らさない。減らすのは出力だけ。**

## explain-tech / explain-code との棲み分け

- **ask(このスキル)**: 一画面で読み切れる短い回答。コードの質問も概念の質問も受ける。
- **explain-tech / explain-code**: 4層構成・用語集・クイズ付きの丁寧な解説。腰を据えて学ぶとき用。

## 入力

`/ask <質問>`

```
/ask この @Transactional(readOnly = true) は何?
/ask SQS の可視性タイムアウトって何?
/ask うちのデプロイの流れってどうなってる?
```

- 引数がなければ「何について知りたい?」と聞き返す。
- 何を聞いているか判別できないほど曖昧なら、1行で「〜のこと?」と確認してから答える。

## 推測で答えない(重要)

- **プロジェクト固有の質問**は、必ず Read / Grep で実際のコードを見てから答える。
- **バージョン依存・フレームワーク固有の話**や自信のない点は、公式ドキュメントや Web 検索で裏を取る。安定した基礎(再帰・クロージャなど)は内部知識でよい。
- 裏が取れなかった点は「要確認」と明記する。

## 回答の形(全体でおよそ10行以内)

1. **結論**: 1〜2行。質問にズバリ答える。
2. **理由・仕組み**: 3〜5行。なぜそうなるか、どう動くか。
3. **根拠**(コードを調べたときだけ): `ファイルパス:行番号` を1行で。

守ること:

- **10行の上限は例外なく守る。**
- コード例は必要なときだけ、1つ・数行まで。
- 見出し・用語集・クイズ・前置き・まとめの繰り返しは付けない。
- 「次に聞くなら」のような深掘りの提案は付けない。次に何を聞くかは読者が自分で決める。
- **広い質問**(複数の仕組みに跨がるもの)は、全体像だけを10行以内で答える。上限を緩めたり、答えずに聞き返したりしない。

## 用語の扱い

- 結論と理由はなるべく平易な言葉で書く。
- 避けられない専門用語には、括弧で数語の補足を付ける(例: 「Reader(読み取り専用の DB)に送る」)。
- 括弧で収まらない用語は、無理に説明を詰め込まずそのまま使う。

## 文体

- 日本語。である調・体言止めを使ってよい(例: 「`readOnly = true` は Reader に振り分ける目印」)。
- 読者を見下さない。「簡単」「当然」などの言葉は使わない。
