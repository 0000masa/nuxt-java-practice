# quick-review

少ないトークンと短い時間でレビューを一巡させるためのスキル。
**コードは修正しない。** 指摘と Before/After の例示だけを出し、実ファイルの編集や git の更新系操作は一切しない（レビュー結果ファイルの出力のみ例外）。

## 入力

`/quick-review [レビュー対象の説明]`

引数は**自由記述**として受け取る。パス・クラス名・メソッド名・日本語が混ざってよい。

- 引数がなければ `git diff --cached`（ステージ済み差分）を対象にする。
- **ステージが空なら**「まだ何も `git add` されていません。レビューしたいパスを指定してください」と伝えて**停止する**。勝手に `git add` してはいけない。

```
/quick-review                                   ステージ済み差分
/quick-review app/Services/VisitorService.php   ファイル全体
/quick-review QRCheckController の check メソッド  メソッド単位
/quick-review VisitorService.php getMonthly     同上（パス＋名前）
/quick-review qr_check.yaml の POST 定義        エンドポイント単位
/quick-review 差分の中の check メソッド          差分に限定
```

## 手順

### 1. 対象を特定する

- **引数なし**: `git diff --cached --stat` → `git diff --cached` の順に実行する。
- **引数あり**: 引数から対象を特定する。ステージ状態は無視し、**リポジトリ全体**から探す。「差分の中の〜」と明示されたときだけ `git diff --cached` に限定する。
  1. パスらしき文字列があれば Glob で解決する。ファイル名やクラス名しかない場合も Glob で探す。
  2. メソッド名・関数名・エンドポイント・見出しの指定があれば Grep で行番号を特定する。
  3. **1 件に絞れたら**「対象: `<パス>:L42-L88`（`QRCheckController::check`）」と一行で明示し、確認は取らずそのまま進む。
  4. **複数候補があれば**最大 5 件を `パス:行番号` 付きで並べて選んでもらう。**0 件なら**近い名前の候補を出して聞き返す。**推測で近そうなものを勝手にレビューしない。**
- **部分指定はコード以外にも適用する**。OpenAPI YAML なら path + HTTP メソッドのブロック、Markdown なら見出しセクションを対象にする。
- **複数の対象**（例: 「check と store」）は目安 3 つまで受け付ける。4 つ以上なら「ファイル全体を見た方が早いのでは」と一言添えて確認する。
- **対象が大きいとき**（目安: 変更 10 ファイル超、または 800 行超）は、本文を読む前に `--stat` の一覧を役割ごとにグループ分けして提示し、「どこから見ますか？（全部も可）」と**一度だけ**確認する。

### 2. 読み込み範囲を絞る

**差分が対象のとき**は、差分を起点に**判断に文脈が要るファイルだけ** Read する。全ファイルを機械的に読まない。

- 新規ファイル、ロジックの変更 → 全文を読む
- typo・文言・設定値だけの変更 → 差分のみで判断する
- 「前後を見ないと判断できない」と感じたときにだけ読む

**メソッド・エンドポイントなど部分が対象のとき**は、それを含む**ファイルは全文読む**（プロパティ、`use` 文、他メソッドとの重複が見えないと判断できないため）。ただし**指摘はその範囲に限定する**。

- 呼び出し先（Service など）は、引数・戻り値の契約を確かめたいときだけ該当箇所を読む。
- 呼び出し元は、変更の影響を確かめたいときだけ Grep する。全件は追わない。

### 3. 統一性の判断材料を集める

- **同種ファイルの兄弟を 1〜2 個** Glob/Grep で探して読む（例: 変更が Controller なら同じディレクトリの代表的な Controller）。部分指定のときは、**まず同じクラス・同じファイル内の他メソッド**と比べ、それでも判断がつかなければ兄弟ファイルを見る。
- **フォーマッタ・リンター設定**（`pint.json` / `.prettierrc*` / `.editorconfig` / `.eslintrc*` / `phpstan.neon` など）があれば読む。**ツールが自動で直すスタイル（インデント、クォート、末尾カンマなど）は指摘しない。**
- `CLAUDE.md` / `README.md` にコーディング規約があれば従う。なければ気にしなくてよい。
- 比較に使ったファイルは、指摘の「根拠」に `パス:行番号` で明記する。

### 4. 観点

一般論よりも**そのプロジェクトの既存の書き方**を優先する。既存と揃っているなら、一般論と違っていても正しいことがある。

#### 4-1. 正しさ・バグ
- 条件の反転、境界値、null / 空配列の扱い、型の不一致
- 例外・エラー時の分岐が抜けていないか
- 変更の影響が及ぶ呼び出し元・呼び出し先と矛盾していないか

#### 4-2. 既存との統一性
- 同種ファイルと構造・命名・責務の置き場所が揃っているか
- 既存のヘルパー・共通処理があるのに独自実装していないか

#### 4-3. 公式作法
- その言語・フレームワークの標準的な書き方か、非推奨の API を使っていないか
- **確信が持てないものはここで判断せず、手順 5 の「要確認リスト」に回す。**

#### 4-4. コメント
- **死んだコードの残り**: コメントアウトされたコード、`dd()` / `var_dump()` / `console.log` の消し忘れ、放置された TODO・FIXME
- **内容の正しさ**: コードを変えたのにコメントや docblock が古いまま、`@param` / `@return` の型が実装と不一致
- **量の適切さ**: 複雑な処理に「なぜそうするか」の説明がない／逆にコードをそのまま日本語にしただけの無意味なコメント
- **書式の統一**: docblock の形式、日本語か英語か、`//` と `/* */` の使い分けが周囲と揃っているか

#### 4-5. セキュリティ
- SQL インジェクション、XSS、認証・認可の抜け（他人のデータが見える経路）
- シークレットのハードコード、ログへの個人情報・トークン出力

#### 4-6. 設計・命名・責務分離
- 命名と実体が合っているか、関数が長すぎないか、重複していないか
- 層をまたいだ責務漏れ（例: Controller にビジネスロジック）
- エラーハンドリングの有無

#### 4-7. テスト
- 変更に対応するテストがあるか
- 異常系・境界値が抜けていないか、アサーションが甘くないか
- 既存テストと書き方（命名、データの作り方、構造）が揃っているか

#### 4-8. パフォーマンス
- N+1 クエリ、ループ内の DB / API アクセス、不要な全件取得
- 差分だけでは判定しにくいので、**確証がないものは指摘しないか【要確認】を付ける**

#### 4-9. ドキュメント（OpenAPI YAML / Markdown など）
- **既存との統一**: 共通スキーマが `components` にあるのに inline で書いていないか、`operationId` / `tags` / `summary` の付け方、エラーレスポンス（401/403/404/422 など）の網羅が他と揃っているか
- **実装との整合**: ルート定義・HTTP メソッド・ミドルウェア、バリデーション規則、レスポンス構造が実装と一致するか。差分に片方しか含まれないときは、もう一方を読んで照合する
- **文章品質**: 誤字脱字、文体（ですます調など）の統一、説明の粒度、用語のぶれ（例:「予約番号」と「予約No」）
- **妥当性**: `$ref` の参照先ファイル・キーが実在するか、キー名のタイポ、仕様として正しい位置にキーがあるか

### 5. 調査（サブエージェント）

- 判断がつかない点は**その場で調べず、「要確認リスト」に溜める**。
- 全対象を見終わってから、**1 回のメッセージで最大 3 エージェントを並列起動**する。1 エージェントに複数の疑問をまとめて渡してよい。
- Agent ツールの指定:
  - `subagent_type: "general-purpose"`
  - **`model: "sonnet"` を必ず指定する。opus は使わない。**
- 依頼文には次を含める:
  - 対象のバージョン（`composer.json` / `package.json` / ライブラリの lock ファイルで先に確認してから渡す）
  - 「公式ドキュメントを根拠に、**結論・理由・参照 URL** を短く返す。推測なら推測と明記する」
- リポジトリ内の調査（類似コード探し、参照先の確認）は**メインが Grep / Read で自分でやる**。エージェントには投げない。
- 調査しても白黒つかない指摘には **【要確認】** を付け、根拠が弱いことを明示する。

### 6. 報告

重要度ラベル:

- **【重要】** バグ・脆弱性・仕様との不整合など、直さないと問題になるもの
- **【推奨】** フレームワークの作法・設計原則・既存との統一性からの逸脱
- **【好み】** どちらでもよいスタイルの話

構成は「冒頭にサマリ、本文はファイル別」:

```
## サマリ
【重要】2 【推奨】5 【好み】1
良い点と全体の傾向を1〜3行。

## <ファイルパス>
### 【重要】L42: 一行で言うと何が問題か
現状: いまどうなっているか
提案: どう変えるか（必要なら短い Before/After）
根拠: 比較したファイルの `パス:行番号`、または調査結果の URL
```

- 良い点はサマリに 1〜3 行だけ書く。
- **指摘がなければ「指摘事項はありません」と短く終える。無理にひねり出さない。**

**部分指定（メソッド・エンドポイントなど）のとき**は、ファイル見出しの下に対象ごとの小見出しを作り、指摘はその一段下の見出しにする。

```
## <ファイルパス>
### check()
#### 【重要】L42: …
### store()
#### 【推奨】L120: …

## 範囲外で気づいた点
- L200 未使用の private メソッドが残っています
```

- ファイル全文を読む過程で**指定範囲外**の問題に気づいたら、末尾の「範囲外で気づいた点」に 1 行ずつ、**最大 3 件**まで添える。
- ただし脆弱性など【重要】相当のものは例外として本体の指摘に上げる。**気づいた重大な問題を黙殺しない。**

### 7. ファイル出力の確認（毎回やる）

報告のあと、AskUserQuestion で必ず聞く。

1. 出力しない
2. `.claude/reviews/review-<YYYYMMDD-HHmm>.md` に出力する
3. パスを指定する（「その他」に入力してもらう）

出力する場合:

- 日時は `date +%Y%m%d-%H%M`、コミットは `git rev-parse --short HEAD` で取得する。
- 先頭にメタ情報を付ける。

```markdown
# レビュー結果
- 日時: 2026-07-31 14:30
- 対象: ステージ済み差分（3ファイル）
- HEAD: 23dace08

## <ファイルパス>
- [ ] 【重要】L42 認可チェックがない
  - 現状: …
  - 提案: …
  - 根拠: …
```

- 本文は画面と同じ内容で、各指摘を `- [ ]` のチェックボックスにする。
- **このファイルは別の AI に渡して修正させるために使う。** 会話の文脈がなくても意味が通るように、指摘ごとにファイルパスと対象を明記する。
- 出力先ディレクトリが無ければ作成する。

## やってはいけないこと

- 実ファイルの編集（レビュー結果ファイルの出力だけは例外）
- `git add` / `git commit` / `git push` などの更新系 git 操作。使うのは `git diff` / `git log` / `git ls-files` / `git rev-parse` などの参照系だけ
- リンター・静的解析・テスト・ビルドの実行（設定ファイルは読むだけ）
- 調査エージェントに `sonnet` 以外のモデルを使うこと
- 確認していないことを断定して書くこと
- プロジェクト固有の情報をスキル内にハードコードしない（他プロジェクトへコピーして使えるようにする）

## 文体

- 日本語、ですます調
- 指摘は「何が・なぜ問題か・どうするか」の順で簡潔に
- 書き手を責めない。事実と提案だけを書く
